WHAT IS IN SCOPE FOR FINDINGS
============================================================

Category A — JAPANESE LANGUAGE ACCURACY (CRITICAL severity)
-----------------------------------------------------------

A1. Incorrect grammar
    - Register stacks: e.g. 「たかいなあですね」 (cannot combine なあ
      casual + です polite + ね). Each register-marker drops on the
      stack.
    - Conjugation errors: ru-verb tagged as u-verb (or vice versa),
      irregular verb (来る / する / 行く) miscategorised.
    - Wrong copula: な-adjective + だ vs です stacking (「きれいだで
      す」 ✗ → 「きれいです」 ✓).

A2. Unnatural collocations
    - Object-particle for 好き / 嫌い / 上手 / 下手 / ほしい / わかる:
      が-particle is the N5-canonical default; を only in specific
      lexicalisations a native catches.
    - て-form chains that mix unrelated actions where a comma /
      separate-sentence would be more natural.
    - Counter-noun collocations (本 for cylinders, 枚 for flat
      objects, 匹 for small animals — register-correct N5 mappings).

A3. Wrong particle
    - は / が default-vs-contrast at N5 level (we test this; we cannot
      ship examples that get it wrong).
    - に vs で for location: に for existence/arrival; で for action-
      location.
    - に vs へ for direction: both work for movement; へ has a
      directional nuance, に has a destination nuance.
    - を vs が with stative verbs (見える, 聞こえる take が; 見る,
      聞く take を).

A4. Wrong reading
    - On-yomi vs kun-yomi assignment per kanji.
    - 一日 = ついたち (1st of month) vs いちにち (one day) — context
      decides.
    - Compound-rendaku triggers (1/6/8/10 → 〜ぴき, not 〜ひき).
    - Sokuon (small ッ) listed as a separate kun-reading rather than
      as a phonological assimilation (e.g. みっつ / よっつ / むっつ /
      やっつ ARE sokuon-allophones of み / よ / む / や, NOT distinct
      readings).

A5. Wrong kanji usage
    - Homograph confusion: 神 (かみ god) vs 髪 (かみ hair) vs 紙 (かみ
      paper) — same reading, different kanji.
    - 上手 (じょうず "skilful") vs 上手 (うわて "upper hand /
      upstream") — same kanji, different reading.
    - 行 covers いく / おこなう — both N5 readings, context-decided.

A6. Onyomi / kunyomi misclassification
    - Sino-Japanese readings (on) vs native Japanese readings (kun)
      mixed up in the kanji.json on/kun fields.
    - Borderline cases (e.g. 茶 only has on-yomi cha/sa at N5; flag
      if a kun-reading is invented).

A7. Vocabulary meaning errors
    - Gloss_en or gloss_hi semantically wrong (e.g. すずしい glossed
      as "cold" — it's "cool" / "pleasantly cool", not 寒い).
    - Polysemy collapse: 上 has multiple senses; the gloss must list
      the senses N5 learners need, not all 6 dictionary senses.
    - Over-narrow gloss: e.g. かける glossed only as "to hang" when
      the N5 corpus uses it for 「めがねを かける」 (to wear glasses)
      and 「でんわを かける」 (to make a phone call).

A8. Mistranslation of Japanese → English
    - English gloss adds a nuance the Japanese doesn't have, or vice
      versa. Test: does the back-translation match?
    - Causative / passive confusion in glosses.

A9. Half-applied ウ音便 in keigo (politeness_ladder.humble)
    - i-adjective + ございます forms must complete the contraction:
        a + u → ō:  たかい → たこう (NOT たかう)
                   ありがたい → ありがとう (NOT ありがたう)
                   はやい → はよう (NOT はやう)
        i + u → yū: おいしい → おいしゅう (NOT おいしう)
                   うれしい → うれしゅう
                   やさしい → やさしゅう
        u + u → uu: やすい → やすう (stays — DO NOT contract)
        o + u → ō:  irregular (e.g. 良う / 無う)
    - Half-applied forms read as broken to natives. Reference cases:
      §3.2.33 in the procedure manual.

A10. Sokuon / rendaku as separate readings
     - 撥音便 / 促音便 outputs (e.g. 一本 いっぽん / 一杯 いっぱい)
       are derived; do not list them as base readings in kanji.json.
     - Rendaku-shifted readings (e.g. 子供 こども vs 三日 みっか)
       are derived; do not list them as separate kun.

A11. Mixed orthography for the same morpheme
     - Pick one convention per surface and stick with it. Examples
       that fail: 時はん vs 時半 in different example sentences for
       the same pattern; ひと vs 人 mixed across the same kanji's
       example list.
     - Bunsetsu-spaced kana vs unspaced (e.g. 「あした がっこうに
       いきます」 vs 「あしたがっこうにいきます」 — pick one for the
       N5 listening / dokkai surface; document the choice).

A12. meaning_ja CROSS-CONTAMINATION (added 2026-05-13; closed by JA-75)
     A failure mode caught 28 times across 3 native-teacher audit
     runs before JA-75 locked it down. The `meaning_ja` field's
     leading 「marker」 must reference the SAME grammar point as the
     entry's `pattern` field. Catastrophic failure mode: meaning_ja
     describes a completely different rule.
     Examples caught (now fixed; documented for reference):
       - n5-110 (counter pattern) had meaning_ja about 〜たい
       - n5-126 (が) had meaning_ja about 〜から、〜
       - n5-142 (〜にします) had meaning_ja about な-Adj+な+めいし
       - n5-154 (もう+ました) had meaning_ja about へ direction
       - n5-183 (Question word + か/も) had meaning_ja about Verb-た+ことがある

     CURRENT GUARDS (in order of strength):
       1. JA-75 (PRIMARY — installed 2026-05-13): per-pattern
          `_meaning_ja_markers` list (internal metadata, snapshot of
          the verified-correct meaning_ja's distinctive vocabulary).
          meaning_ja must contain at least 2 markers, OR at least 1
          distinctive (>=3-char) marker. Catches future drift AWAY
          from the verified state — including subtle 1-char-overlap
          cases that JA-71 missed.
       2. JA-71 (SECONDARY): character-overlap heuristic. Still
          green; serves as a coarse first-line check. Limitation:
          single-char incidental overlap (も, が, で) lets contamination
          pass — that's why JA-75 supersedes it.

     What JA-75 STILL cannot catch:
       - Edits that PRESERVE the marker vocabulary but reword the
         actual meaning (rare; would require LLM semantic comparison).
       - Authoring of a brand-new pattern where the markers themselves
         get authored incorrectly from the start.
     For these, manual native-teacher sampling remains the catch-all.

A13. PITCH-ACCENT MORA COUNT ERRORS (added 2026-05-13)
     Tokyo NHK convention: each kana = 1 mora, EXCEPT small kana
     (ゃゅょぁぃぅぇぉ) merge with the preceding mora; ー and っ are
     each 1 mora. Common failure modes from LLM-authored entries:
       - げんき (3 mora, ge-n-ki) listed as mora=1
       - しずか (3 mora, shi-zu-ka) listed as mora=1
       - 先週 せんしゅう (4 mora) listed as mora=1
       - おにいさん (5 mora, o-ni-i-sa-n) listed as mora=4
       - おいしい (4 mora, o-i-shi-i) listed as mora=3
     Verify pitch_accent.mora == count_mora(reading) by hand for any
     sampled entry. The kanjium dictionary at
     not-required/tools-archive/_cache_kanjium_accents.txt has the
     canonical values for all 1009 N5 entries. CI invariant JA-70
     locks this forward.

A14. PLACEHOLDER / SELF-INCRIMINATING TEXT IN SHIPPED DATA (added 2026-05-13)
     Look for text that admits the entry is incomplete or wrong:
       - "(Fallback ref:)" prefix in public_domain_refs.context
       - "PD pending until 20XX" in pd_status (with year >= 2026)
       - "TODO" / "FIXME" / "see above" / "placeholder" anywhere in
         user-visible fields
       - "(This pattern is also indexed as 'X')" parentheticals in
         explanation_en (use structured see_also field instead)
     These betray that the entry was authored as a placeholder and
     never replaced. CI invariant JA-69 catches the legal-status
     version (pd_status admissions of in-copyright).

A15. OFF-PATTERN BOILERPLATE AT EXAMPLE INDICES [4][5][6]
     (added 2026-05-14; surfaced during the 2026-05-14 native audit)

     A pervasive anti-pattern in grammar.json: indices [4], [5],
     and [6] of MANY patterns contain canned filler sentences that
     do NOT demonstrate the target pattern. Worst-case offenders
     pre-cleanup:
       "あなたは がくせいですか。"          in 21 patterns
       "あなたは どなたですか。"           in 18 patterns
       "どうして 来ませんでしたか。―..."     in 17 patterns
       "じぶんで しゅくだいを します。"      in 14 patterns
       "あにより わたしのほうが はやく ..."  in 14 patterns
       "父に とけいを もらいました。"        in 11 patterns
     ...etc.

     Pattern: pick a random grammar pattern with `tier: late_n5` or
     a conjugation-form pattern (Verb-X, い-Adj-X, な-Adj-X) and
     check whether indices [4][5][6] contain examples that USE the
     target pattern's marker. Examples to verify against:

       n5-044 こう/そう/ああ/どう → [4][5][6] previously held
         てください request sentences (くちを あけて ください, etc.)
         that don't demonstrate manner-demonstratives.

       n5-104 Verb-stem + たいです → [5][6] previously held
         "なぜ来なかったのですか" / "しけんはむずかしかったです" —
         neither uses たいです.

       n5-167 〜んです/〜のです → [4][5][6] previously held plain
         です sentences (no んです at all).

     Output format for findings:
       Pattern: <n5-XXX>
       Index: [N]
       Issue: example does not demonstrate the pattern's marker
         (target marker: "<...>", example: "<ja>")
       Fix proposal: <new sentence using the marker, preserving form tag>

     CI gate: JA-81 (boilerplate-leak guard at threshold 10
     patterns) already catches the extreme cases. The mid-range
     (3-9 occurrences) requires this manual audit.

A16. FORM-TAG VALUE MISMATCHED WITH EXAMPLE CONTENT
     (added 2026-05-14)

     Every example object has a `form` field whose value is one of
     {affirmative, past, negative, question, habitual, ...} OR a
     pattern-specific role tag (e.g. "weather-agreement",
     "exclamation-beautiful"). The value must MATCH the example's
     grammatical form:

       form="past" example MUST contain past marker (〜た, 〜ました,
         〜でした, 〜かった, 〜だった, 〜んだ)
       form="negative" example MUST contain negative marker (〜ない,
         〜ません, 〜じゃない, 〜では ない, 〜なかった, 〜なくて)
       form="question" example MUST end with か / ？ / の / よね /
         かな / だろう / でしょう

     Common mismatch patterns:
       - form="question" but example is a の-final informal Q tagged
         as affirmative (or vice versa)
       - form="past" tagged on a negative-non-past example (e.g.
         "じゃ ありません" tagged past — that's present-negative)
       - form="affirmative" tagged on an opinion-question ending in
         ですか

     False positive to skip: relative-clause past markers appear
     mid-sentence (e.g. "わたしが 買った 本" / "I bought the book")
     — the た is on the verb modifying the noun, not at sentence
     end. Don't flag these.

A17. WITHIN-PATTERN DUPLICATE EXAMPLES
     (added 2026-05-14)

     Same `ja` string appearing at two different indices in one
     pattern wastes a slot. Almost always introduced by a content-
     authoring pass that didn't check sibling examples before
     authoring a new one.

     Detection: for each pattern, build a dict of ja → index. Any
     ja value seen twice is a duplicate.

     Fix policy: keep the first occurrence; replace the second with
     a newly-authored sentence demonstrating the same pattern + same
     form tag, using N5-vocab + N5-kanji only.

A18. VOCAB EXAMPLE TEMPLATE-LEAK: 'Xを 見ました。'
     (added 2026-05-15; locked by JA-83)

     Anti-pattern: data/vocab.json carried 108 entries whose example
     at index [1] was the literal template 'Xを 見ました。' →
     "I saw X." The Japanese is grammatical but semantically weak
     for many headwords:
       - 'おとうとを 見ました。'   "I saw younger brother." (unnatural)
       - 'けさを 見ました。'       "I saw this morning." (nonsense)
       - 'なつを 見ました。'       "I saw summer." (nonsense)
       - 'となりを 見ました。'     "I saw next to." (nonsense)
       - 'まいばんを 見ました。'   "I saw every night." (nonsense)
     The English translations are also broken — most omit the
     article ("I saw wall.", "I saw pork."), confirming bulk LLM
     generation without review.

     Detection regex (strict; require X is a single token, no
     whitespace, so legitimate sentences like 'どうぶつえんで ぞうを
     見ました。' / "I saw an elephant at the zoo" pass through):

         ^[^\s]{1,10}を\s*見ました(?:よ|ね|よね)?。?$

     Fix policy: replace with a natural N5-level sentence that uses
     the headword in a different semantic frame
     (e.g. Xを 買いました / Xが すきです / Xに 行きます / Xを つかいます).

     CI gate: JA-83 prevents future regression.

A19. VOCAB EXAMPLE TEMPLATE-LEAK: 'あの Xは どこですか。' for
     non-location headwords
     (added 2026-05-15; locked by JA-83)

     Anti-pattern: 111 entries used 'あの Xは どこですか。' →
     "Where is that X?" at index [1] where X is a time word, body
     part, abstract noun, or other non-location concept:
       - 'あの 九月は どこですか。'       "Where is that September?"
       - 'あの ときは どこですか。'        "Where is that time?"
       - 'あの おとといは どこですか。'    "Where is that day before yesterday?"
       - 'あの けいかんは どこですか。'    "Where is that police officer?"
     Locational `どこ` is appropriate for places (the trash entry
     for ホテル would naturally read 'ホテルは どこですか。'). For
     non-location headwords, the question is nonsense.

     Detection (skip when entry.section starts with 13-locations
     or 26-house):

         pat = re.compile(r"^あの\s+(.{1,10})は\s*どこですか。?$")
         m = pat.fullmatch(ja)
         if m and not is_locationish and m.group(1).strip() == form.strip():
             flag

     Fix policy: replace with a natural sentence using the headword
     in context appropriate to its semantic class (time → 'Xに 〜',
     body part → 'Xが いたいです', person → 'Xは 〜さんです', etc.).

A20. VOCAB EXAMPLE TEMPLATE-LEAK: 'これは Xです。' / 'あれは Xです。'
     bare introduction on entries with 3+ examples
     (added 2026-05-15; locked by JA-83)

     Anti-pattern: 178 noun entries used bare 'これは Xです。' /
     'あれは Xです。' / 'それは Xです。' at example[1] where the
     entry already has 3 or more examples. These bare templates
     waste an example slot:
       - 'これは お母さんです。'   "This is mother." (no article in EN)
       - 'あれは 男です。'         "That is man." (bare)
       - 'これは えです。'          "This is picture." (bland)
     The template is fine for an INTRODUCTORY example; it becomes
     filler when the entry has 3+ examples and other slots already
     demonstrate the headword.

     EXCEPTION: for the demonstrative-pronoun entries themselves
     (これ / それ / あれ / この / その / あの), 'これは Xです。' IS
     the canonical demonstration of the headword. Do NOT flag for
     entries with section/pos in the 5-demonstratives family.

     Detection:

         pat = re.compile(r"^(これ|あれ|それ)は\s*(.{1,10})です。?$")
         is_demonstrative = (entry.pos == "demonstrative" or
                             "demonstrative" in entry.section.lower())
         if pat.fullmatch(ja) and not is_demonstrative \
            and len(entry.examples) >= 3:
             flag

     Fix policy: replace with a natural usage of the headword
     (e.g. 'Xは どこですか。', 'Xを 〜', 'Xが 好きです。').

A21. VOCAB EXAMPLE TEMPLATE-LEAK: '「X」と あいさつしました。' where
     X is not a greeting
     (added 2026-05-15; locked by JA-83)

     Anti-pattern: 12 entries in sections 36-greetings and 39-fillers
     used '「X」と あいさつしました。' → "I greeted with X." even when
     X was a non-greeting filler:
       - '「えーと」と あいさつしました。'   (えーと = "um/uh")
       - '「いいえ」と あいさつしました。'   (no isn't a greeting)
       - '「ええ」と あいさつしました。'     (yes isn't a greeting)
       - '「そうですか」と あいさつしました。' (response, not greeting)

     Detection:

         pat = re.compile(r"^「(.{1,10})」と\s*あいさつしました。?$")
         GREETINGS = {"おはよう","こんにちは","こんばんは","ありがとう",
                      "さようなら","おやすみ","ただいま","おかえり",
                      "もしもし","いってきます","いってらっしゃい",
                      "おかげさまで"}
         m = pat.fullmatch(ja)
         if m and m.group(1) not in GREETINGS:
             flag

     Fix policy: change the verb to 言いました or restructure into a
     more natural usage (e.g. '「えーと」と 聞きました。', '「いいえ、
     ちがいます」と 言いました。').

A22. VOCAB CROSS-ENTRY BOILERPLATE (the JA-81 analogue for vocab)
     (added 2026-05-15)

     A single ja sentence appearing as an example in 5 or more vocab
     entries is suspicious. Some reuse is legitimate when each entry
     teaches a different word in the same sentence — e.g. the
     sentence 'コーヒーは 飲みますが、にくは たべません。' naturally
     appears under コーヒー, にく, 飲む, 食べる. But the threshold for
     "natural reuse" is much lower than for grammar (where JA-81 uses
     10). When the count hits ≥ 5, audit each occurrence:
       - KEEP if the entry's headword is genuinely demonstrated by
         that part of the sentence.
       - REPLACE if the entry's headword is incidental (the sentence
         could have been written without it). Example: the counter
         まい entry using 'まいにち にほんごを べんきょうします。' —
         that's 毎日, not the counter 枚.

     Threshold: ≥ 5 → audit. The 2026-05-15 pass diversified 5
     sentences (8x→4x, 7x→2x, three 5x→3-4x) using this rule.

A23. VOCAB HEADWORD-MISSING-FROM-EXAMPLE
     (added 2026-05-15)

     Every example sentence must use its entry's headword somehow.
     Examples that don't contain the headword are silent bugs: the
     learner sees the example but doesn't see the word being taught.

     Detection: for each example, check that ja contains AT LEAST
     ONE of:
       - the entry's `form`
       - the entry's `reading`
       - any string in entry.readings[] (for multi-reading entries)
       - a verb stem (for verb entries) — see A23a
       - a counter-rendaku alternant (for counter entries) — see A23b

     Failure mode: 'たばこ' entry had example 'バスで 学校へ 行きます。'
     at [1] — about bus/school, no たばこ at all. Real bug.

     A23a. Verb-stem awareness (so まつ→まちます counts as a hit):
            verb-1 (godan): drop the final u-row kana
              まつ → ま; かう → か; よむ → よ; はたらく → はたら
            verb-2 (ichidan): drop the final る
              たべる → たべ; おきる → おき; ねる → ね
            verb-3 (irregular):
              する → し / す ; くる → こ / き / く
              -する compounds: べんきょうする → べんきょう
            Compound -くる verbs (e.g. もってくる, つれてくる):
              prefix + {き, こ, く} all count as headword stems.

     A23b. Counter rendaku (so 三びき counts as a ひき hit):
             ひき → {ぴき, びき}     (一ぴき, 三びき, 八ぴき)
             はい → {ぱい, ばい}     (一ぱい, 三ばい)
             ふん → {ぷん}          (一ぷん, 三ぷん)
             ほん → {ぽん, ぼん}     (一ぽん, 三ぼん)
             ほ   → {ぽ, ぼ}
             かい → {がい}          (三がい floor counter)
             けん → {げん}

     Fix policy: replace the example with one that uses the headword
     in inflected or rendaku-altered form.

A26.1 KANJI.JSON SENTENCES BORROWED FROM A GRAMMAR PATTERN /
     REDUNDANT-ENGLISH PAIR (added 2026-06-07)

     Anti-pattern: a kanji's `sentences[]` array carries two example
     sentences whose English translations are identical or near-
     identical (e.g. 雨: "あした 雨だろう" / "あした 雨でしょう" - both
     "It'll probably rain tomorrow"). Almost always a sign the pair was
     lifted from a GRAMMAR pattern (here だろう vs でしょう register
     contrast) to illustrate the grammar, not the kanji. On a kanji
     page the second sentence then adds no kanji-usage value.

     Detection: within each entry's sentences[], flag any two whose
     translation_en is equal after lowercasing + stripping trailing
     punctuation, OR whose JA differs only by a known register-pair
     token (だろう/でしょう, だ/です, the like).

     Fix policy: keep ONE, replace the other with a varied everyday
     sentence that teaches the kanji in a different context (different
     verb / time / place). Kanji example sentences must teach the
     TARGET kanji's everyday usage - not be a vehicle for a grammar
     contrast. Corpus scan 2026-06-07: 雨 was the only affected entry.

A27. DOKKAI MONDAI RANGE IS 4-6 (NOT 1-4 LIKE LISTENING)
     (added 2026-05-15)

     N5 dokkai mondai numbering is DIFFERENT from listening:
       問題4: short single-question passages
       問題5: mid-length multi-question passages
       問題6: information retrieval (signs / menus / brochures)
     N5 listening uses 1-4 instead:
       問題1: task understanding
       問題2: point understanding
       問題3: utterance expression
       問題4: quick response

     Detection mistake to avoid: a "valid mondai 1-4" check for
     reading.json or papers/dokkai will false-flag legitimate mondai
     5 and 6 entries. Use the correct per-surface range.

A37. COUNTER-NOUN SEMANTIC PAIRING
     (added 2026-05-15 native-teacher pass; JA-89 lock1 prevents
     re-introduction of the specific mis-pairings caught in this pass)

     Even when the counter is grammatically possible, examples that
     pair a noun with a counter from a non-canonical set teach
     learners a non-preferred pairing. JLPT N5 has the following
     primary pairings (context-dependent exceptions exist; this is
     the textbook-default mapping, not a closed enumeration of all
     valid pairings):

       本 (ほん/ぼん/ぽん) → cylindrical objects: pens, bottles,
                            umbrellas, trees
       枚 (まい)          → flat thin objects: paper, photos,
                            tickets, plates, shirts
       冊 (さつ)          → bound books / magazines / notebooks
       個 (こ)            → small / general 3D objects: apples,
                            eggs, balls
       人 (にん, ひとり/ふたり) → people
       匹 (ひき/ぴき/びき) → small animals: dogs, cats, fish (live),
                            insects
       頭 (とう)          → large animals: horses, cows, elephants
       台 (だい)          → machines / vehicles
       杯 (はい/ぱい/ばい) → cupfuls / glasses of liquid
       軒 (けん, N4)      → buildings / houses (defer)
       足 (そく)          → pairs of footwear (shoes, socks)
       つ (native count)  → general fall-back; OK for ~10 objects

     Anti-pattern (caught 6 instances in 2026-05-15 pass): native-
     counter-series teaching entries 三つ..九つ used 「本が Xつ
     あります」. While grammatically possible, books canonically
     take 冊. Replace with a noun that's natively つ-paired (りんご /
     ボール / いす / コップ / はこ).

     Detection: for each `<num><counter>` token, walk backwards to
     the noun bound by particle (を/が/に/も). Look up the noun in
     canonical-pairing table. Flag if counter ∉ valid set for that
     noun.

     CRITICAL false-positive avoidance:
       - 倍 (ばい) is a multiplier suffix (三倍 = "triple"), NOT a
         noun-counter. Exclude from the scan.
       - 「Xの Yを N counter」 — the closer noun (Y) is the counted
         one, not the modifier (X). Use rightmost match.

     Fix policy: replace the example noun with a canonically-paired
     one OR change the counter to the canonical one for that noun.

A38. ANIMACY VIOLATIONS: ANIMATE NOUN + が あります
     (added 2026-05-15 native-teacher pass; locked by JA-89 lock3)

     Animate nouns (people / animals) must use います for existence.
     Inanimate nouns use あります. Violations:
       - 男の子が あります        → must be 男の子が います
       - 日本人が あります        → must be 日本人が います
       - スペイン人が あります    → must be スペイン人が います
       - そぼが あります          → must be そぼが います

     Detection: maintain an ANIMATE_NOUNS list. For each sentence,
     scan for `<animate-noun>(?:は|が)\s*あります`.

     CRITICAL false-positive avoidance: substring matches. The
     pattern 「ぼうしが あります」 (hat — inanimate) must NOT match
     because うし (cow, animate) is a substring of ぼうし. Use
     `(?<![ぁ-ゟ一-鿿])<noun>` lookbehind to require word-start.

A39. BARE-ARTICLE EN: "There is X." for singular common noun
     (added 2026-05-15 native-teacher pass; locked by JA-89 lock2)

     74 vocab examples had translation_en of the form 「There is
     hat.」 (missing article) or 「I see boy.」 (same). Pattern is
     templated and the EN is ungrammatical for singular common

     Flag all others.

     Detection regex: `^(There is|There are|I (?:see|eat|have|
     drink|use)) ([a-z]+)\.?$` with the noun NOT in the allowed-bare

A41. UNNATURAL ADVERB-VERB PAIRINGS
     (added 2026-05-15 native-teacher pass)

     Some adverbs require specific verb-mood pairings:
       - ぜひ + volitional / request / want: ぜひ 来てください ✓,
         ぜひ 食べたい ✓ — but NOT plain ぜひ 食べます (the adverb
         expects choice or desire, not flat declaration).
       - ただ + casual / minimization: ただの 水 ✓, ただ 見るだけ ✓
         — but NOT bare ただ ごはんを 食べます (ambiguous between
         "just/only" and "free", semantically thin).
       - やはり + opinion-confirmation: やはり 〜が 好きです ✓ —
         can pair with neutral declarative but feels heavy without
         contrast context.

     Caught at the vocab.adverb entries' example[1] slot. Fix by
     pairing the adverb with the right verb mood.

A42. POTENTIAL/EXISTENTIAL VERB + VOLITIONAL つもり MISMATCH
     (added 2026-05-15 native-teacher pass)

     つもり ("intend / plan to") attaches to volitional verbs (verbs
     of intentional action). It does NOT pair with:
       - 聞こえる (potential / spontaneous "be audible") — caught
         at vocab 聞こえる[1]: 「あした 聞こえるつもりです」 is
         "I plan to be audible tomorrow" — nonsense.
       - ござる (existential keigo, equivalent to ある) — caught
         at vocab ござる[1]: 「あした ござるつもりです」 is "I plan
         to exist tomorrow" — nonsense.
       - Intransitive change-of-state verbs like はじまる / しまる /
         おちる (caught at the template-leak in A43 below).

     intransitive / spontaneous is wrong.

A46. PITCH ACCENT VALIDATED AGAINST EXTERNAL REFERENCE
     (added 2026-05-15; locked by JA-90)

     The vocab.json `pitch_accent.drop` field stores an integer drop-
     mora position per entry. Drop position is auditory phenomenology
     — LLM training has limited explicit accent annotation and
     confidence on this dimension is genuinely lower than on syntax
     or morphology.

     **Reconciliation methodology (2026-05-15):**

     1. Fetch external reference dataset (kanjium project, CC-BY-SA
        4.0). The dataset compiles from EDICT/EDRDG and NHK 日本語
        発音アクセント新辞典. Pin to a specific upstream commit SHA
        for reproducibility.

     2. Filter to N5 vocab scope by (form, reading). Use a TWO-TIER
        matching approach:
          - Tier 1: exact (form, reading) match
          - Tier 2: reading-only fallback (for N5 entries with kana-
            only forms where kanjium has the kanji-first form)
        Save the filtered subset to `data/n5_pitch_accent_reference.json`
        with full `_meta` block (source, commit SHA, license,
        attribution, regenerate_with command).

     3. Per-entry classification:
          - MATCH: current drop ∈ reference drops → confidence='high'
          - DISAGREE: current drop ∉ reference drops → fix to
            reference[0], confidence='high', log diff
          - NOT_FOUND: vocab not in reference → confidence='unverified',
            keep current value (transparent gap)

     4. Add `pitch_accent.confidence` field to EVERY vocab entry
        (Option C transparency). Values: 'high' | 'medium' | 'low' |
        'unverified'. JA-90 enforces:
          confidence='high' AND drop ∈ reference_drops, OR
          confidence in {'medium', 'low', 'unverified'}

     **N5 2026-05-15 reconciliation results:**
        MATCH:           810/1009  (80%)
        DISAGREE_FIXED:   22/1009  ( 2%)
        NOT_FOUND:       177/1009  (18%) — gairaigo + function words
     Total kanjium-validated: 832/1009 (82%) at confidence='high'.

     **Caveats embedded in the methodology:**
        - Tokyo dialect bias (kanjium reflects standard); Kansai/
          Kyushu accent maps differ entirely
        - by-reading matches use UNION of all drops across kanjium
          entries with that reading — wider but less precise
        - NOT_FOUND entries (mostly loanwords) genuinely lack a
          reference; native-human auditory review remains queued

     **For Nx levels:** apply this same pattern in audit cycle 4-5
     (after structural + linguistic saturation). The refresh tool at
     `tools/refresh_pitch_accent_reference.py` is reusable across
     levels — just point at the level's vocab.json.

A47. AUDIO RENDERER NORMALIZATION GAP — bunsetsu-space particle drop
     (added 2026-05-14; caught on n5-008.8 user-reported audio mismatch)

     The audio renderer (`tools/build_audio_voicevox.py`) MUST strip
     JLPT-textbook bunsetsu spaces from the displayed `ja` field
     before passing text to VOICEVOX. The displayed text uses spaces
     for learner readability (e.g., `コーヒーと こうちゃを かいました。`);
     VOICEVOX uses OpenJTalk for prosody, and OpenJTalk treats each
     space as a hard token boundary that inserts an inter-bunsetsu
     pause. The particle trailing a bunsetsu (the を at end of
     `こうちゃを`) gets stress-weakened or devoiced at that pause
     boundary, producing audio where the displayed particle is
     INAUDIBLE — the learner hears `コーヒーと こうちゃ かいました。`
     even though `pitch_marks` and the `/audio_query` phoneme
     analysis confirm を IS rendered.

     **Detection at audit time:**
     1. For every grammar example with audio + a bunsetsu space
        followed by a particle (`を` / `が` / `に` / `で` / `と` /
        `も` / `へ`): listen to the rendered MP3, verify every
        particle is audible.
     2. Programmatic proxy: render the same text via VOICEVOX
        `/audio_query` with spaced vs stripped input; compare
        `pause_mora` counts. If spaced version has ≥2 more inserted
        pauses, the particle-devoicing risk is real.
     3. File-size proxy: spaced-input renders are ~30-50% larger
        than stripped-input renders for the same sentence (because
        of the inserted pauses). An audio file ~50% larger than its
        stripped-input sibling is a red flag.

     **Fix pattern (single repo-line in the renderer):**
       text = text.replace(" ", "").replace("　", "").replace("\t", "")
     Applied BEFORE the `/audio_query` call. The display JSON keeps
     the spaces; only the TTS input is normalized.

     **Corpus-wide impact:** caught after one user-reported example;
     the bug affected ALL 1782 grammar examples re-rendered in the
     2026-05-12 VOICEVOX batch (commit `c28266d`). Resolution required
     a `--force` corpus-wide re-render after the script was patched.
     ~15 min CPU time with 4 workers.

     **Cross-engine:** the same pause-boundary class affects gTTS,
     VOICEVOX, edge-tts, Azure JA, OpenAI TTS, and any OpenJTalk- or
     morphological-analyzer-based engine. The legacy gTTS renderer
     (`tools/build_audio.py`) had `normalize_for_tts()` for exactly
     this reason; the VOICEVOX renderer dropped it during the flip.

     **For Nx levels:** any pipeline that consumes display text MUST
     normalize whitespace at render time. Add a Phase-0 check: assert
     that the renderer's text-transform call exists in source (regex
     for `.replace(" ", "")` in the build_audio_*.py file).

A48. VERB-CLASS PARTICLE DISAMBIGUATION IN wcp / common_mistakes
     (added 2026-05-16; caught on user-reported BUG-002)

     wrong_corrected_pair (wcp) and common_mistakes entries that
     disambiguate Japanese particles by VERB CLASS can mislabel an
     N5-canonical form as "wrong" when the rationale conflates two
     distinct verb classes (companion-と verbs vs direction-に verbs).

     **The specific N5 case (BUG-002):** pattern n5-008 (LIST-EXHAUSTIVE
     と) had wcp[2] stating:
       wrong:    ともだちに あいました。
       correct:  ともだちと あいました。
       why:      会う meaning "meet (mutual)" takes と; に is
                 grammatical but more like "happen to encounter".

     Both errors:
     - 会う is N5-canonical with に (Genki I L4, Minna no Nihongo, JEES
       samples). The "happen to encounter" rationale was fabricated.
     - The entry was off-pattern: n5-008 covers LIST-EXHAUSTIVE と (joining
       nouns), not the companion-と vs direction-に *verb-class*
       distinction.

     **Per-verb canonical particle table (N5 scope):**
       会う (meet)             → に  (direction-of-meeting)
       行く / 来る (go/come)   → に / へ (direction)
       遊ぶ (play with)        → と  (companion / joint action)
       話す (talk)             → と  (mutual action)
       結婚する (marry)        → と  (mutual action)
       テニスを する (joint X) → と  (companion)
       出会う (encounter)      → に
       挨拶する (greet)        → に  (direction)

     Any wcp whose `why` says "[verb] takes [particle]" without
     identifying the verb's class is over-generalized. Always state
     "this verb class takes X" rather than "Japanese takes X".

     **Detection at audit time:**

     - For every wcp / common_mistakes entry whose `wrong` field uses
       a Person-に or Person-と construction with a verb: cross-check
       the verb against the per-verb canonical table.
     - Phase-0 candidate: regex scan for ともだちに 会|あ, ともだちに
       話, ともだちと 行 (canonical forms used as `wrong`); flag for
       manual review. The flag rate is low (1 in 534 wcps at N5)
       so manual triage is feasible.

     **Fix pattern:**

     - If the wcp's verb is in the per-verb table as taking [particle],
       and the wcp marks [particle] as wrong → flip OR replace the wcp
       entry with a verb of the OTHER class (so the `wrong → correct`
       pair illustrates a real error).
     - Update the `why` field to name BOTH verb classes explicitly.
     - Mark `provenance: user_bug_NNN_fix_YYYY_MM_DD` for traceability.

     **Caveats:**

     - The verb-class assignments above apply at N5; higher levels
       may have register-flexible verbs (e.g., 出会う in literary
       context, 〜と) where both are acceptable. Reconfirm at Nx.

     - **LLM-as-judge per example.** Run a cheap LLM-yes-no pass

     - JA-91: cross-pattern explanation_en Levenshtein < 0.85.
     - JA-92: per-example JA-content-word ∩ EN-content-word > 0.

     - For (a): rewrite explanation_en against the canonical Japanese

A50. MORA-COUNT SYSTEMATIC ERROR IN pitch_marks
     (added 2026-05-16; caught on user-reported BUG-004)

     The `mora` integer per pitch_marks entry was computed by an
     under-counting heuristic. 911 entries in grammar.json had
     stored mora ≠ correctly-counted morae.

     **Canonical rule (single source of truth):**

       Each kana counts as 1 mora EXCEPT the small kana
       ゃ ゅ ょ ぁ ぃ ぅ ぇ ぉ (and their katakana equivalents)
       which COMBINE with the preceding kana.
       The long-vowel mark ー counts as 1 mora.
       The sokuon っ counts as 1 mora.
       The moraic ん counts as 1 mora.

     **Canonical algorithm (use this verbatim — under 5 lines):**

       SMALL_KANA = set("ゃゅょぁぃぅぇぉャュョァィゥェォ")
       def count_mora(kana_string):
           return sum(1 for c in kana_string if c not in SMALL_KANA)

     **Common error shapes observed:**

     - Counts ー as 0 (コーヒー stored 3, actual 4 — 48 instances).
     - Counts ん as 0 (ごはん stored 2, actual 3 — 49 instances).
     - Counts small ゃ/ゅ/ょ as 1 (over-counting digraphs).
     - Counts terminal kana as 0 (truncation off-by-one).

     **Detection at audit time:**

     - Walk every pitch_marks entry corpus-wide; recompute via
       count_mora(); diff against stored. Any mismatch is a bug.
     - Run as a HARD gate, not advisory — a wrong pitch_mark mora
       can break the audio TTS prosody hint and the pitch-contour
       UI overlay.

     **CI invariant to add:** JA-93 — pitch_marks.mora ==
     count_mora(pitch_marks.form) for every entry. Build fails on
     mismatch.

     **Sample regression check (run before commit):**

       python -c "
       import json; SMALL=set('ゃゅょぁぃぅぇぉャュョァィゥェォ')
       d=json.load(open('data/grammar.json',encoding='utf-8'))
       bad=[(p['id'],pm['form'],pm['mora'],sum(1 for c in pm['form'] if c not in SMALL))
            for p in d.get('patterns',[]) for ex in p.get('examples',[])
            for pm in ex.get('pitch_marks',[])
            if pm.get('mora') != sum(1 for c in pm['form'] if c not in SMALL)]
       print('Pitch mora mismatches:', len(bad))
       "
       # Expected: 0

A52. RIGHT/WRONG FRAMING FOR GRAMMATICALLY-VALID ALTERNATIVES
     (added 2026-05-16; caught on user-reported BUG-007;
      same class as BUG-002 — recurring)

     A common_mistakes entry labels a grammatically correct,
     N5-canonical Japanese sentence as "WRONG" because it isn't the
     form the author happens to prefer for that specific context.
     The opposite form is then labeled "RIGHT". WHY field sometimes
     even admits "either is correct" but the labels stay.

     **Failure modes observed (N5):**

     - n5-127 cm[2]: けれども marked WRONG vs けど marked RIGHT —
       けれども is the formal full form; WHY field even said "either
       is correct semantically."
     - n5-105 cm: 行きたくありません marked WRONG vs 行きたくないです
       marked RIGHT — both correct; register difference only.
     - n5-023/051/052/053/054/055/056/057 cm: 〜ね confirmation-seeker
       sentences labeled WRONG vs 〜か questions labeled RIGHT —
       〜ね vs 〜か is pragmatic register, not grammaticality.
     - n5-069 cm: 「あさごはんを たべて から、…」 (canonical 〜てから)
       labeled WRONG.
     - n5-071 cm: 「まって ください ね。」 (natural polite softener)
       labeled WRONG.

     **Pedagogical cost:** a learner trusts the RIGHT/WRONG dichotomy.
     Once they internalize "けれども is wrong," they will avoid a
     valid formal form for life — and Japanese-speaking adults will
     perceive their output as register-flat.

     **Fix framing — replace "WRONG vs RIGHT" with one of:**

     - "In *casual* speech, A is the natural choice; B carries
       *formal* register and is appropriate when …"
     - "Register variants — both correct; pick A in *context X*, B
       in *context Y*."
     - "Either is correct. A is more common in *speech*; B is more
       common in *writing/textbooks*."

     **Authoring rule (apply on every new common_mistakes entry):**

     Before marking any form WRONG, ask:
       - Is the form *ungrammatical*? Then yes, label WRONG.
       - Is the form merely *register-mismatched* or *less common*?
         Then DO NOT label WRONG; use one of the framings above.

     **Detection at audit time:**

     - Phase-0 grep: every common_mistakes entry's `wrong` value, run
       a grammatical-validity LLM judge ("Is this sentence
       grammatically correct Japanese as a standalone utterance?"
       YES/NO). Any YES is a candidate for rewrite — surface for
       review.

     **CI invariant family:** JA-91 (introduced) + this class can be
     gated by a Phase-0 audit pass rather than a binary CI gate,
     since "grammatically correct" requires semantic judgment.

     **Related label-integrity check (form/category chips, 2026-05-29):**
     Beyond common_mistakes WRONG/RIGHT labels, the grammar example `form`
     field (the green scenario chip rendered in the SPA, e.g.
     "<object>-request") can drift from the sentence via copy-paste — a new
     example seeded from a sibling keeps the old label. Caught by a user:
     n5-149 rendered "water-request" on "ペンを ください / Please give me a
     pen" (fixed to "pen-request"). CI JA-171 guards the physical-object
     subset (object named in the label must appear in translation_en).
     FALSE-POSITIVE class to NOT touch: grammatical/scenario heads
     (plain / negative / speed / repeat / attention -request) are not object
     mismatches — they describe the request's manner/context.

A53. FOLK-LINGUISTIC GRAMMAR TERMINOLOGY IN common_mistakes
     (added 2026-05-16; caught on user-reported BUG-008)

     A common_mistakes WHY rationale explains a particle/form choice
     with grammar-class terminology that doesn't survive scrutiny
     against actual Japanese-pedagogy references.

     **Canonical instance (N5):**

     - n5-004 cm[0] said: "あう (to meet) is intransitive in Japanese
       — it takes に, not を."
     - Reality: 会う takes に because it is a contact/encounter verb
       (相手を必要とする動詞), not because it is intransitive. Many
       transitive verbs take に. 会う itself is sometimes classified
       as transitive in 国語辞典 (the 相手 is grammatically the
       object). The intransitive label is a folk shortcut that
       misleads about how particle assignment actually works.

     **Other risk shapes (predict for Nx):**

     - "Transitive/intransitive" used loosely for verbs that take
       non-を arguments.
     - "Subject/topic" used as synonyms (は marks topic, が marks
       subject; sometimes the topic IS the subject, sometimes it
       isn't — the distinction is real and must not be collapsed).
     - "Passive/causative" voice labels applied to constructions
       that aren't passive/causative in any standard analysis.
     - "Auxiliary verb" applied to constructions that aren't
       auxiliaries.

     **Fix framing — describe the verb's actual argument structure:**

     "会う takes the encounter-target with に. The person you meet
     is the に-marked partner — this is a property of
     encounter/contact verbs, independent of transitivity
     classification."

     **Authoring rule:** if a WHY rationale uses a grammar-class
     label (intransitive, topic, subject, auxiliary, passive,
     causative, etc.), the usage must match the term as used in
     Genki, Tobira, or A Dictionary of Basic Japanese Grammar. Folk
     shortcuts get rewritten in terms of the actual grammatical
     behavior.

     **Detection at audit time:**

     - Phase-0 grep for "intransitive", "auxiliary", "passive",
       "causative", "subject", "topic" in common_mistakes WHY fields.
       Each hit gets manual review against a reference grammar.

A54. PATTERN-PARTICLE MISMATCH IN CANONICAL EXAMPLES
     (added 2026-05-16; caught on user-reported BUG-009)

     A pattern teaches a specific particle X, but one or more of its
     canonical examples uses a different particle Y in the slot the
     pattern is supposed to demonstrate. Learners pattern-match by
     example, so a mismatch forms a wrong association.

     **Canonical instance (N5):**

     - n5-003 (が particle) ex[6]: 「わたしは がくせいです。」 — uses
       は, not が. Pattern teaches が; example demonstrates は.

     **Detection at audit time — particle-presence assertion.**

     For each pattern whose `pattern_form` field or pattern title
     names a specific particle (が, を, に, で, と, へ, から, まで),
     require ≥1 occurrence of that particle in each example JA.
     Position check is heuristic — particle should sit between
     content words, not just appear as part of an unrelated compound.

     For patterns where the pattern-defining feature is OBLIGATORY
     が (interrogative-subject contexts, identificational predicates,
     existential clauses), additionally require an interrogative
     head (だれ / なに / どれ / どこ / いつ / どの-NP / どんな-NP)
     OR an existential predicate (います / あります) in the example.

     **CI invariant to add:** JA-95 — particle-pattern alignment.
     Per-example check; build fails if a pattern's canonical particle
     is absent from ≥30% of its examples (or absent from ANY example
     for strict particle-introducing patterns like n5-003).

     **Authoring rule (apply on every new example):**

     Before filing example E under pattern P with canonical particle X,
     verify E.ja contains X in a position consistent with what P
     teaches. If E doesn't, the example belongs in a different
     pattern.

     import json

A57. SCHEMA-LEVEL REGISTER-VARIANT DETECTION IN common_mistakes
     (added 2026-05-16; caught on user-reported BUG-011 —
      schema-level follow-on to BUG-007 / A52)

     **Problem class:** A52 (BUG-007) caught the case where a
     common_mistakes WHY rationale said "both forms are correct"
     while the surface still labeled one as WRONG and the other as
     RIGHT. The WHY rewrites landed, but the underlying
     `wrong`/`right` field-name dichotomy stayed. UI rendering uses
     red strike-through for the `wrong` cell and green check for
     the `right` cell — so the visual contradiction with the WHY
     text remains.

     **Detection at audit time — three signals:**

     1. **Field-name + WHY-text contradiction.** Scan every
        common_mistakes entry where the WHY field contains any of:
        "both are correct", "either is correct", "register choice",
        "natural choice", "formal", "casual", "more natural",
        "pragmatic, not grammatical", "valid form", "both valid".
        Each hit MUST carry `kind: "register_variant"` (the schema
        marker from BUG-011's fix). Bare entries with those WHY
        phrases but no `kind` field are regressions.

     2. **Cell content with explicit-context markers.** A `wrong`
        or `right` cell that contains a parenthetical context tag
        (e.g. "(in casual speech)", "(in formal writing)",
        "(too casual for a formal report)", "correct but rigid")
        indicates a register-variant pair, not a grammatical error.
        Set `kind: "register_variant"`.

     3. **Pattern-keyed variant.** A `wrong` form that exemplifies
        a different N5 pattern from the one being taught (e.g.
        n5-173 cm[2] uses しないと いけない, which is the n5-175
        pattern, not the n5-173 〜なくてはいけない form). Also a
        register_variant by this schema (`label_a` / `label_b`
        identify the two patterns).

     **CI invariant (queued):** JA-NN — for every
     common_mistakes entry, if WHY contains a register-variant
     phrase OR cell contains a context parenthetical, assert
     `kind == "register_variant"`. Build fails on regression.

     **Sample regression check:**

     ```python
     import json, re
     G = json.load(open('data/grammar.json', encoding='utf-8'))
     VARIANT_WHY_PHRASES = re.compile(
         r'both are correct|either is correct|register choice|'
         r'pragmatic, not grammatical|natural choice|both valid|'
         r"both forms? (are|is) (grammatically )?valid|"
         r'register variant|formal full form|casual contraction',
         re.I,
     )
     VARIANT_CELL_PHRASES = re.compile(
         r'\(in casual|\(in formal|\(too casual|\(too formal|'
         r'correct but rigid|register|register-mismatch',
         re.I,
     )
     # Disqualifiers: WHY phrases signaling a GENUINE grammar error
     # (not a register variant). Skip these so we don't false-flag
     # entries like "casual contraction can't combine with です".
     ERROR_DISQUALIFIERS = re.compile(
         r"don'?t combine|cannot combine|sounds wrong|ungrammatical|"
         r"grammatically incorrect|never\s+(?:takes|use|valid)|"
         r'is wrong because',
         re.I,
     )
     bad = []
     key_regressions = []
     for p in G.get('patterns', []):
         for i, cm in enumerate(p.get('common_mistakes', []) or []):
             why = cm.get('why', '') or ''
             # After BUG-013, register-variant entries use form_a/form_b
             # (not wrong/right). Check both shapes for compat.
             form_a = cm.get('form_a') or cm.get('wrong') or ''
             form_b = cm.get('form_b') or cm.get('right') or ''
             if ERROR_DISQUALIFIERS.search(why):
                 continue  # legitimate error, not a register variant
             needs_variant = (
                 VARIANT_WHY_PHRASES.search(why)
                 or VARIANT_CELL_PHRASES.search(form_a)
                 or VARIANT_CELL_PHRASES.search(form_b)
             )
             if needs_variant and cm.get('kind') != 'register_variant':
                 bad.append((p['id'], i, why[:60]))
             # BUG-013: register-variant entries must use form_a/form_b
             # keys, not wrong/right. Any straggler is a regression.
             if cm.get('kind') == 'register_variant' and ('wrong' in cm or 'right' in cm):
                 key_regressions.append((p['id'], i))
     print(f'A57 unflagged register-variant entries (target 0): {len(bad)}')
     print(f'A57 stale-key regressions (register_variant + wrong/right; target 0): {len(key_regressions)}')
     for b in bad[:5]:
         print(f'  {b}')
     ```

     **Cross-reference:** F.19 in
     `JLPT Common/procedure-manual-build-next-jlpt-level.md`. The
     class has now surfaced 3 times in 2 days (BUG-002 →
     BUG-007 → BUG-011); gate at authoring time, not at audit.

Category B — JLPT N5 SCOPE LABELING (HIGH severity)
---------------------------------------------------

B1. N4-or-above grammar treated as N5 without late_n5 / borderline
    flag. Known N4-leakers to specifically check:
    - 〜について, 〜に関して, 〜に対して — N3+ topic markers.
    - 〜ばかり — N4.
    - 〜たら conditional (sequence/result) — N4.
    - 〜ても concession — N4-edge.
    - 〜ながら + relative clause — N4.
    - 〜たり〜たりする with multiple actions — N4 expansion of N5
      core.
    - 〜ようにする / 〜ようになる — N4.
    - Passive 〜られる / causative 〜させる — N4.

B2. N4+ vocab without `tier: late_n5` or `tier: borderline_n4`
    Known leakers (seen in past audits):
    - 紹介する, 卒業, 大学院, 雑誌, 階段, ポケット (some of these
      ARE N5; verify against jlptsensei / Tanos / Marugoto tables).

B3. N4+ kanji without exception-list documentation
    - 田舎, 億, 銀, 黒, 風, 呂, 雑, 誌, 紹, 介, 卒, 業, 舎, 荷 —
      cross-check against data/n5_kanji_whitelist.json.

B4. Example sentences using N4+ kanji or vocab in N5-core patterns
    - Pattern-level tier might be N5, but its example uses 紹介する.
      Flag for vocab swap OR tier downgrade.

B5. Dokkai passages with kanji-density exceeding N5 cap
    - Per-passage kanji-cardinality rule: ≤2 N4-borderline kanji per
      passage, all whitelisted via the JA-28 exception list.

Category C — PEDAGOGICAL QUALITY (MAJOR severity)
-------------------------------------------------

C1. Explanations that confuse N5 learners
    - Too abstract — define by USE, not by linguistic theory at N5.
    - Too many alternatives in one breath — pick the canonical form,
      mention alternates separately.
    - Wrong audience assumption (assuming familiarity with Japanese
      linguistic terminology — 連用形 / 連体形 — at N5).

C2. Missing learner-critical cautions
    - 寝る (ru-verb) vs 寝ない irregular pattern — common L2 trap.
    - 来る / 行く forward/away from speaker confusion in te-form.
    - 〜たい vs 〜たがる person-marking restriction.

C3. Missing distinction between near-synonyms
    - すき vs だいすき (intensity).
    - いい vs よい (register: いい casual, よい slightly more formal).
    - もう / まだ (already / still / not-yet — perfective/imperfective).
    - 〜たい vs ほしい (verb-volition vs noun-desire).

C4. Ambiguous meaning fields
    - あめ (rain / candy) — both N5. Gloss must disambiguate or list
      both with reading context.
    - はし (bridge / chopsticks / edge) — pitch-accent + context.
    - おもい (heavy / think) — different verbs.

C5. Overly broad meanings for beginner kanji
    - 上 has 5+ dictionary senses; N5 needs at most 2-3.
    - 下 same constraint.
    - 行 needs to highlight いく (go) at N5, OK to add おこなう (carry
      out) for N4 — flag if the N4 sense is in the N5 file without
      tier flag.

C6. Inconsistent terminology across files
    - "transitive" vs "vt." vs "他動詞" — pick one convention.
    - "Group 1 / Group 2 / Group 3" vs "u-verb / ru-verb / irregular".

C7. Easy-Japanese (やさしいにほんご) register violations
    When a field is labeled with the 「やさしいにほんご」 register tag
    (typically in `meaning_ja` rendered in the UI as 意味（やさしい
    にほんご）), the content MUST follow the accessibility-tier rules
    (弘前大学 やさしい日本語 guidelines / NHK NEWS WEB EASY register):
    - One idea per sentence; ≤30 characters.
    - N5-floor vocab only — no しつもん (N4), について (N3),
      に関して (N3), 〜ばかり (N4), 〜ばかりでなく.
    - No double negative, no passive voice, no causative.
    - Concrete examples (「あさ ごはんを たべました」), not abstract
      definitions.
    - If kanji used, give furigana / bunsetsu-spaced kana.
    Reference: §3.2.25 in procedure manual.

C8. Pattern-title quality
    - No placeholder POS-only labels (e.g. "Verb", "Adjective + Noun",
      "Particle"). Each pattern title must be specific enough to be
      searchable + memorable.
    - Examples of acceptable titles: 「V-plain + N (relative clause)」,
      「Adj + N (combined)」, 「V-plain + まえに」.

Category D — TEST / QUESTION QUALITY (HIGH severity)
----------------------------------------------------

D1. Questions not at N5 level
    - Stem or choices include N4+ vocab without proper labeling.
    - Reading passage too dense, too long, or too abstract.

D2. Multiple possible correct answers
    - Particularly common with interchangeable particle pairs (に/へ
      for direction, は/が in narrow contexts). Flag any question
      where 2+ choices are pragmatically valid without scene context.

D3. Ambiguous distractors
    - Distractors that overlap semantically with the correct answer
      such that a native couldn't choose definitively.
    - Distractors that are technically wrong for one reason but
      could be argued correct on another.

D4. Wrong correct-answer key
    - The "correctAnswer" field doesn't match the intended target;
      check rationale text vs answer index.

D5. Distractor quality
    - Too easy: all 4 are wildly different POS / category — gives
      the answer away.
    - Too advanced: distractor uses N3+ structure to test an N5
      point.
    - Unnatural: distractor is grammatical but no native would say
      it that way.
    - Length-symmetry: 4 choices should be roughly similar in
      character count for moji-style questions.

D6. Ko-so-a-do questions lacking scene context
    - これ vs それ vs あれ is determined by spatial/conversational
      proximity. Without scene-setting in the stem, the question is
      ambiguous. Reference: §3.2.4 + §C.2 in procedure manual.

D7. Placeholder distractor explanations
    - "See pattern detail" or "Refer to grammar.json" in
      rationale_en / rationale_hi — flag as MAJOR. Each distractor
      explanation must teach why the wrong answer is wrong.
    - Reference: §3.2.3.

D8. Filler-MCQ smell
    - When the question feels auto-generated rather than authored —
      uniform sentence templates across many questions, distractors
      that look picked at random from a vocab list, no testable
      learning point. Reference: §3.2.1.

A59. READING.JSON BATCH-DRIFT — 6 FIELD DIVERGENCES BETWEEN
     AUTHORING BATCHES (BUG-041..046, added 2026-05-17;
     locked by JA-104, JA-105, JA-106)

     reading.json's 54 passages were authored in two batches:
     the original 45 (`n5.read.001..045`) and a later batch of 9
     (`n5.read.046..054`). The later batch used DIFFERENT
     conventions across 6 fields. Both batches passed the
     existing JA-* invariants because the schema was permissive
     for those fields. The drift signature: divergences cluster
     by batch (not random), and every divergent field on the new
     batch differs from the prior batch — pointing to an
     authoring-convention change that wasn't captured as a
     contract.

     The 6 manifestations (each becomes a sub-audit when the
     pattern shows up on a future corpus):

     A59.1 LEGACY ENUM FIELD WITH MIXED SEMANTICS (BUG-041)
       Field `level` carried 4 mixed-semantics values across the
       corpus: `easy` / `medium` (intended use — difficulty),
       `N5` (the JLPT level, redundant with the corpus filename),
       `info-search` (a passage TYPE, redundant with
       `format_role`). One field cannot mean "difficulty AND
       JLPT-level AND passage-type." Decompose. Fix: rename to
       `difficulty`; closed enum {easy, medium, hard}; map "N5"
       → "medium" for the 9 newest passages. Drop "info-search"
       (already in `format_role`). Lock: JA-104.

     A59.2 MULTI-LANGUAGE INLINE FIELD (BUG-042)
       Field `summary` carried mixed JA + EN + HI on 45 passages
       in the shape `"じこしょうかい (self-introduction विषय
       परिचय)।"` and JA-only on 9. HI was ALREADY in
       `summary_hi`, so the inline HI was a double-encoding.
       Fix: normalize `summary` to JA-only; move parenthetical
       EN to `summary_en_extracted`. Authoring rule:
       locale-specific content uses locale-suffixed fields, not
       positional in-field delimiters.
       SUB-LESSON (regex/parsing): the 45 mixed summaries
       terminated with Devanagari danda `।` (U+0964), not the
       Japanese full-stop `。`. A normalizer regex written with
       only `。` matched 0 of 45 entries. When string-parsing
       multi-locale data, the terminator class must include
       every locale's punctuation, not just the "primary."

     A59.3 _META DOCUMENTATION DRIFT (BUG-043)
       `_meta.schema_additions` did not list `format_type:
       "notice"` (a value actually present in the data) and
       still referenced a `comprehension` format_type that
       BUG-044 was removing. `_meta` is loaded by consumers —
       treat it as data, not documentation. Fix: rewrite
       `_meta.schema_additions` to match post-fix shape. Rule:
       when a fix changes a field's shape, update `_meta` in
       the same commit.

     A59.4 CONCEPTUAL FIELD DUPLICATION ACROSS TWO KEY NAMES
       (BUG-044)
       Both `format_type` and `format_role` co-existed on
       passages. For 9 passages, both held `"comprehension"` —
       a passage TYPE, which belongs in `format_role`.
       `format_type`'s intended use is the info-search visual
       SUBTYPE (`schedule_table` / `menu_list` / `notice`).
       Fix: keep `format_type` for the narrow subtype semantic;
       drop the bleed value from comprehension passages. Lock:
       JA-106 (`format_type ∈ {null, schedule_table, menu_list,
       notice}`).

     A59.5 FIELD-SHAPE DIVERGENCE — LIST OF STRINGS vs LIST OF
       OBJECTS (BUG-045)
       `vocab_preview` was a list of vocab_id STRINGS on 45
       passages (Shape A) and a list of DICTS `[{vocab_id,
       form, reading, gloss}, ...]` on 9 (Shape B). Shape B
       denormalized info already in vocab.json — risking
       stale-snapshot drift. Fix: normalize to Shape A
       (list of vocab_id strings). Consumers resolve
       form/reading/gloss via vocab.json. Rule: prefer
       ID-references over embedded copies when the referenced
       data lives elsewhere. Lock: JA-105.

     A59.6 PRONOUN-FORM INCONSISTENCY ON CANONICAL TEXT
       (BUG-046)
       45 passages used わたし (kana); 9 used 私 (kanji). The
       N5 whitelist includes 私. The newer batch had implicitly
       standardized on kanji; the older 45 hadn't been
       back-migrated. Fix: string-replace わたし → 私 on the
       older 45 (26 replacements across 23 passages); update
       each passage's `kanji_used` to include 私. Authoring
       rule: when a policy change is made mid-corpus, propagate
       to ALL prior entries before merging the new batch.

     DETECTION SIGNAL (the meta-class): if `corpus[i]` has a
     field set with one shape/value-class and `corpus[j]` has
     the same field with a different shape/value-class, AND the
     split lines up cleanly with entry-creation order (or with
     any other metadata facet — author / source / batch ID),
     suspect batch-drift. Random authoring noise spreads across
     the corpus; batch-drift clusters.

     OPERATIONAL RULE: after any "add N new entries" pass on a
     corpus that has prior entries, run a same-shape audit
     against the prior batch — for every field on the new
     entries, does the field exist on the prior entries with
     the same value-shape, enum, locale split? The audit
     catches the drift at merge time, not 6 months later when a
     downstream consumer breaks.

INTENTIONAL CROSS-LEVEL REGISTER SURFACES
-----------------------------------------

These fields are DESIGNED to show N3+ register variation for
pedagogical context. They are explicitly exempted from JA-13
(out-of-scope-kanji invariant) via SKIP_SUBTREE_FIELDS in
tools/check_content_integrity.py. DO NOT generate findings flagging
N3+ vocab / kanji as out-of-scope when they appear in:

- `politeness_ladder.respectful` (e.g. 〜られる尊敬語 forms)
- `wrong_corrected_pair` (intentionally shows native-grade wrong/right
  pairs; N4+ vocab in the "wrong" example is THE POINT — it
  illustrates a real error a learner would make)
- `common_mistakes` (Japanese illustration uses native vocab)
- `cultural_context` (background notes use whatever Japanese is
  needed for the cultural point)
- `summary` (pedagogical commentary uses normal Japanese)
- `authentic_citations` (textbook bibliographic metadata — chapter +
  context note format, uses normal Japanese for the meta-commentary)

DO flag actual Japanese errors (wrong conjugation, wrong particle,
half-applied ウ音便, etc.) inside these surfaces — they are exempted
from kanji-scope-only, not from Japanese-correctness.

LOCALE-SUFFIXED TRANSLATION FIELDS
----------------------------------

These hold L1 translations (Hindi, English) — never apply Japanese
grammar / orthography rules to them:
- meaning_hi, meaning_en
- explanation_hi, explanation_en
- gloss_hi, gloss_en
- summary_hi, summary_en
- title_hi, title_en
- prompt_hi, prompt_en
- description_hi, description_en
- note_hi, note_en
- meanings_hi, meanings_en
- Any field ending in _hi, _en, _vi, _id, _ne, _zh.

Hindi prose carrying Japanese grammatical particles must use kana
not romaji (R-1.1 invariant JA-41) — that IS in scope.

MOCK-PAPER FORMAT ADHERENCE — paper-distractor exception
--------------------------------------------------------

data/papers/moji/, data/papers/goi/, data/papers/bunpou/ use the
official JLPT exam-paper format where DISTRACTORS may use N4+ kanji
to test recognition. Flag only if the CORRECT ANSWER uses out-of-N5
kanji. Reference: JA-40 invariant.

NORMALIZATION CASES THAT ARE INTENTIONAL

- いい / よい — both forms are correct N5; documented inconsistency

- Some patterns use 漢字 form in stems and 仮名 form in choices —
  this is testing kanji-reading, not orthographic inconsistency.

LESSONS LEARNED FROM 2026-05-13 AUDIT SESSION (calibration)

This audit prompt was sharpened during a 2026-05-13 audit cycle that

ERROR-RATE FLOORS BY CATEGORY (what to expect even on a "clean" corpus):
  - Cross-contaminated meaning_ja: WAS 1-3 per run; NOW close to
    zero after JA-75 installed (2026-05-13, commit b9b0ac5). Subtle

  - LLM-derived pitch_accent.mora errors: ~30% on LLM-authored;
    ~0% on kanjium-dictionary-derived. Use kanjium values when
    available.

AD-HOC-SAMPLING ANTI-PATTERN (NEW 2026-05-13):
  Across three accuracy-audit runs in a single day, each run found
  new issues that the prior run missed — NOT because the corpus
  changed, but because each run sampled DIFFERENT dimensions:
    Run 1: cultural register, on-yomi convention, topic tags
           → caught F-1, F-2, F-3
    Run 2: placeholders, repeated-kana, double-particles
           → caught F-4, F-5, F-6
    Run 3: form-field consistency, cross-locale, audio refs
           → caught F-7 (520 missing form values!)
  The form-field check (anti-§3.2.34) was IN THE PROMPT'S OWN
  anti-pattern list at run 1; it just wasn't structurally checked
  until run 3. The lesson: prose anti-pattern bullets are not a
  substitute for executable checks. Phase 0 (mandatory checklist)
  exists to prevent this recurrence.

  Rule: never claim "I audited X" if you didn't actually execute
  the structured check for X. Sampling is for naturalness; structural
  checks are for presence/consistency.

RUN-4 LESSON: BOOTSTRAP-WITH-WRONG-STATE class (added 2026-05-13):
  Run-4 (after the 3 native-teacher runs + 3 accuracy runs)
  caught n5-166: a set-greetings pattern whose meaning_ja described
  the の particle instead. Failure chain:
    1. Some prior run/edit replaced n5-166's meaning_ja with content
       from a different pattern (likely a cleanup-cascade artifact
       from G-2 or T-2 schema migrations 2026-05-13).
    2. The install_ja75_marker_dict.py auto-extractor blessed the
       broken text — its markers became BOTH pattern-side
       (いただきます/ごちそうさま/おはようございます from pattern field)
       AND content-side (めいしと/めいしを/つなぎます from broken text).
    3. JA-71 passed via the fallback pass (any pattern kana appears
       somewhere in meaning_ja — set-greeting hiragana shared trivial
       chars い/ま/す/は with the meaning_ja).
    4. JA-75 passed because markers were auto-extracted from the
       broken text — they self-matched.
    5. Three native-teacher audits + 3 accuracy audits + 1 prior
       N5Improvement run all missed it. CHECK-6 (a stricter
       reimplementation of JA-71 without fallback) caught it on
       run-4.

  Tried JA-80 (meaning_ja ↔ meaning_en Japanese-substring overlap)
  as a CI invariant; reverted with 19 false positives. The class
  requires LLM-level semantic comparison and stays in the manual-
  sample domain (CHECK-31 above documents the procedure).

  Procedural lesson: when bootstrapping any "snapshot of current
  verified-correct state" (like JA-75's markers), do NOT auto-
  extract from the live text unless that text has been independently
  verified. Either (a) manually curate the snapshot from canonical
  authoring sources, or (b) cross-check the snapshot against the
  pattern's meaning_en BEFORE blessing it. install scripts that
  bootstrap from the data file inherit any contamination already
  present.

DRIFT BETWEEN PROMPT CURRENT-STATE TABLE AND LIVE DATA:
  Every audit-refresh script encoded in this prompt risks using
  WRONG FIELD NAMES (anti-pattern: name drift from authoring batch
  to consumer audit). The 2026-05-13 N5Improvement run-1 had 7
  wrong field-name lookups (pitch vs pitch_accent, mnemonic_visual
  vs mnemonic.visual, etc.) producing false "0%" readings on 4
  P1 items that were ALREADY DONE. Always verify field names
  against live data structure before claiming "X is missing."

  Estimate in turns / tool-calls / commits, NOT person-days. A
  "10-12 day audit cycle" routinely closes in ~10 turns of

FP-1. ウ音便 contraction where o+u → ō has no visible spelling change
      (added 2026-05-14)

      Examples of CORRECT forms that some checkers flag as
      "half-applied ウ音便":
        おもしろう ございます  ← おもしろい (omoshiroi) → onbin
                                  drops く: omoshirou → o+u → ō
                                  Written: stays as おもしろう because
                                  the long ō is spelled with う in
                                  modern Japanese (cf. ありがとう).
        あおう ございます      ← あおい (aoi)   → o+u → ō
        あかう ございます      ← あかい (akai)  → a+u → ō (written
                                  あこう in some styles; both accepted)

      Compare CORRECT contractions where spelling DOES change:
        おいしゅう ございます  ← おいしい — i+u → yū (spelling changes)
        たこう ございます      ← たかい  — a+u → ō (spelling changes:
                                  たかう → たこう)

      RULE OF THUMB: vowel before う in the onbin form:
        - "a" → spelling changes to "o" (たかう → たこう)
        - "i" → spelling changes to "yū" (おいしう → おいしゅう)
        - "o" → spelling stays "ou" (おもしろう, あおう)
        - "u" → spelling stays "uu" (やすう)

      If the auditor sees a form already-ending-in-"ou"+ございます,
      check whether the i-adjective stem ended in "o" before flagging.

FP-2. Past-marker mid-sentence in relative clauses
      (added 2026-05-14)

      Example: わたしが 買った 本 (the book I bought)
      Form tag: "past"
      Naive end-of-sentence check: NO past marker found (sentence
        ends in "本" which is a noun).
      Reality: 買った IS the past form, just inside a relative clause
        modifying 本. The form-tag is correct.

      RULE: a sentence with a relative-clause modifier on the LAST
      noun phrase doesn't end with the past marker, but is still
      past-tense overall. Don't flag.

FP-3. Mixed kanji/kana orthography within one pattern
      (added 2026-05-14)

      Example: pattern n5-007 で has 学校 (kanji) in [2] and がっこう
        (kana) in [7]. Both are accurate Japanese; the project has
        no enforced single-spelling convention.

      This IS a real style/consistency issue (see §3.2.17 in the
      procedure manual), but it is NOT a language-ACCURACY bug.
      Surface as a style note, NOT a CRITICAL finding.

FP-4. Cross-pattern reuse of canonical sentences below threshold-10
      (added 2026-05-14)

      Example: "わたしは がくせいです。" appears in 9 patterns. All
      9 are basic copula / identity patterns where the sentence IS
      a legitimate canonical example. The CI gate JA-81 catches
      sentences at frequency 10+; below that, manual judgment
      applies.

      RULE: only flag cross-pattern reuse when EITHER:
        (a) frequency ≥ 10 (JA-81 would fail);
        (b) frequency ≥ 4 AND ≥2 of the occurrences are in patterns
            whose marker is NOT visible in the sentence (genuine
            misplaced boilerplate, not canonical reuse).

FP-5. Counter rendaku in headword-presence checks
      (added 2026-05-15)

      Counter vocab entries headed ひき / はい / ふん / ほん / etc.
      legitimately appear in examples as ぴき / ばい / ぷん / ぽん
      (rendaku / handakuon alternation triggered by preceding number):
        - n5.vocab.9-counters-common.ひき [2] = 'うちには ねこが 三びき います。'
        - n5.vocab.9-counters-common.はい [0] = 'コーヒーを 一ぱい 飲みました。'
      These are CORRECT examples. A naive substring check for "ひき"
      in the ja text will miss "びき" and false-flag. Apply the
      rendaku alternant set (see A23b) before flagging.

FP-6. Compound -くる verbs in headword-presence checks
      (added 2026-05-15)

      Compound verbs ending in くる (e.g. もってくる, つれてくる)
      conjugate on the くる auxiliary:
        - もってくる → te-form もってきて, past もってきました
      The kana "くる" never appears in conjugated examples. A naive
      substring check misses these. Expand the stem set to
      prefix + {き, こ, く} for any reading containing くる.

FP-7. Demonstrative-pronoun entries using 'これは Xです。'
      (added 2026-05-15)

      For these entries: これ, それ, あれ, この, その, あの, here-style
      and there-style demonstratives in section 5-demonstratives.
      Examples like 'これは ほんです。' / "This is a book." are the
      CANONICAL demonstration of the headword. They are not
      boilerplate — the headword is the demonstrative itself, and
      the template IS the lesson.

      RULE for A20 (KORE-BARE template): skip when entry.pos =
      "demonstrative" OR section contains "demonstrative". The
      A20 detector hard-codes this exception.

FP-8. English translations with trailing parenthetical annotations
      (added 2026-05-15)

      Vocab examples often carry pedagogical annotations after the
      sentence terminator:
        - "I am a student. (topic は)"
        - "Good morning. (formal)"
        - "It is my book. (possessive の)"
      The sentence itself IS terminated; the annotation is metadata.
      A naive "ends with .?!" check sees the closing ")" and false-
      flags. Strip trailing /\s*\([^)]*\)\s*$/ BEFORE checking for
      terminator.

FP-9. authentic.json `reading` field is the FULL phrase read-aloud
      (added 2026-05-15 wave-1)

      The authentic.json schema's `reading` field captures the
      verbalised pronunciation of the WHOLE ja phrase, not the
      single-vocab-entry reading. For card auth.menu.koohii:
        ja:      'コーヒー 350円'           (the signage as written)
        reading: 'コーヒー さんびゃくごじゅうえん'  (how a Japanese speaker
                                            would read the sign aloud)
        vocab_refs: ['n5.vocab.18-drinks.コーヒー']  (which vocab entries
                                                    appear inside)
      A cross-corpus reading-vs-vocab.json check that doesn't condition
      on "ja == canonical form" will false-flag 16 such multi-word
      signage cards. Apply the check ONLY when ja matches a single
      vocab form exactly.

FP-10. English/short-technical rationales for paper-question answers
       (added 2026-05-15 wave-3)

       Paper-question rationales are often brief English paraphrases
       or grammar-tag micro-explanations that legitimately don't share
       Japanese characters with the (Japanese) correct answer:
         answer '来ました'      rationale 'past affirmative (came one
                                          month ago).'
         answer '220えん'       rationale '1000 - (100×3) - (120×4) =
                                          1000 - 300 - 480 = 220.'
         answer 'まいにち'       rationale '毎 (マイ) + 日 (ニチ).'
       A char-overlap heuristic between correct-answer and rationale
       flags 115 of 402 paper-questions as misaligned, but manual
       triage finds only ~2% are real misalignments. Flag only when
       the rationale CLEARLY describes a different passage segment
       than the answer (see A30).

FP-11. ひとりでに ("by oneself") is a fixed adverb, not a particle stack
       (added 2026-05-15 wave-2)

       The substring 「でに」 appears inside the compound adverb
       「ひとりでに」 (= "by oneself / spontaneously", e.g. 「まどが
       ひとりでに あきました」 = "the window opened by itself").
       This is a single lexicalised word, not 「で」 + 「に」 stacked
       as separate particles. A regex catching「でに」 as an illegal
       particle stack must use a lookbehind `(?<!ひとり)` to exclude
       this fixed expression.

FP-12. 〜いです IS the correct polite-affirmative form of an i-adj
       (added 2026-05-15 native-teacher pass)

       The form `<i-adj-stem>いです` (e.g. 「おもしろいです」,
       「おいしいです」, 「あついです」) is the CANONICAL polite-
       affirmative form of an i-adjective. It is NOT the "should-be
       くて" wrong-conjunction form. The genuinely wrong forms are:
         <stem>いで、 (should be <stem>くて、)
         <stem>いでは  (should be <stem>くては)
         <stem>いでも  (should be <stem>くても)
       A regex catching the wrong forms MUST exclude `で(?=す)` from
       the trigger set, or it will false-flag 240+ correct polite-
       affirmative forms across the corpus.

FP-13. 倍 (ばい) is a multiplier suffix, not a noun-counter
       (added 2026-05-15 native-teacher pass)

       三倍 (sanbai = "triple"), 二倍 (nibai = "double") attaches to
       numbers as a multiplier suffix. It is NOT a noun-counter (no
       「Xを 三倍」 with a real noun). A counter-noun-pairing audit
       (A37) must EXCLUDE 倍 from the counter token set. Otherwise
       「三ばいに なりました」 (became triple) will be flagged as a
       noun + counter pair.

FP-14. i-adjective inflected forms still demonstrate the headword
       (added 2026-05-15 native-teacher pass)

       i-adjectives inflect by dropping the final い:
         dictionary:    おもしろい
         te-form:       おもしろくて
         negative:      おもしろくない
         past:          おもしろかった
         adverbial:     おもしろく
       Any of these inflected forms CONTAINS the i-adj headword
       semantically — the entry IS being demonstrated. A naive
       substring search for the full dictionary form 「おもしろい」
       will miss 「おもしろく / おもしろくて / おもしろかった」 and
       false-flag the example as "headword missing". The check must
       also accept stem-only (drop final い) as a valid match.

       Same caveat for verb-3 'する' standalone (stems are 'し' and
       'す', not just 'する'): 「しゅくだいを します」 contains 'し'
       (in します), so the headword IS present.

FP-15. ぜひ / ただ + neutral declarative — semantically thin, not a
       grammar bug
       (added 2026-05-15 native-teacher pass)

       Adverbs ぜひ and ただ have natural pairings:
         ぜひ + volitional / request: ぜひ 来てください, ぜひ 食べたい
         ただ + minimization:         ただの 友だち, ただ 見るだけ
       A neutral-declarative pairing like 「ぜひ ごはんを 食べます」
       is grammatically valid but semantically thin — the adverb
       adds nothing meaningful. This is a pedagogical-quality issue
       (caught at vocab.adverb entries' example[1] slot), not a
       grammar error. Treat as "should improve" not "must fix".

FP-16. register_variant entries falsely flagged as empty wrong/right
       (added 2026-05-24 v4 test-review session)

       `grammar.json` `common_mistakes` and `wrong_corrected_pair`
       arrays may contain entries with `kind: "register_variant"`.
       These carry a DIFFERENT schema:
         form_a / form_b      (both forms — both valid)
         label_a / label_b    (style labels: "neutral" / "polite" / …)
         why                  (explains the register contrast)
       The entry is teaching register *variation*, not error correction.
       Both forms are grammatically correct; there is no wrong/right.

       Origin: BUG-011 introduced this schema (HTML rendering carries
       a `.variant-pair` CSS class with neutral framing — no
       strike/check icons, unlike normal wrong/right pairs).

       A naive auto-check looking for empty `wrong`/`right` strings
       will flag every register_variant entry. In the 178-pattern N5
       corpus, this produced 38 false-positive "empty row" findings.

       RULE for any auto-check / export / test-scenario tool that
       reads `wrong`/`right` from common_mistakes or
       wrong_corrected_pair: short-circuit on
       `kind == "register_variant"` BEFORE reading wrong/right.
       Tools updated this session:
         tools/grammar_auto_checks.py        (skips register_variant)
         tools/export_grammar_for_review.py  (preserves `kind` through pipeline)
         tools/grammar_horizontal_checks.py  (skips register_variant)
         tools/fix_class_e_paren_context_2026_05_24.py (skips register_variant)

       Also: tools that update `data/index.json` size_bytes must use
       the LF-normalised byte count (matches JA-125 calculation), not
       `os.stat().st_size` — on Windows CRLF inflation makes the
       on-disk size ~77KB higher than what the integrity check
       expects for grammar.json.

WRITING DISCIPLINE FOR AUDIT DOCS
(added 2026-05-15 — applies to every audit report, coverage doc,
reconciliation doc, and CI-invariant description string)
============================================================

Audit output is read by future maintainers, native-human reviewers,
institutional adopters, and learners. Absolutist language in audit
docs misleads them about what we actually know. Apply the following
rewrites WITHOUT being asked, before committing any audit-related
prose:

REWRITE TABLE (absolutist → bounded):

  "every X" / "all X"
    → "every X *in the corpus snapshot scanned*"
       OR "every X *we sampled*"

  "0 findings" / "0 real findings"
    → "0 findings *against the N patterns scanned*"
       OR "0 findings *in this sample*"

  "RESOLVED" / "complete" / "final"
    → "addressed for M of N items in scope"
       OR "narrowed via <method>; <K> items remain unverified"
       OR "as of commit <SHA>"

  "closed enum"
    → "closed against currently-observed values"
       OR "enum-locked to the values currently shipping;
           future additions would need explicit enum extension"

  "JA-NN locks the gain"
    → "JA-NN prevents re-introduction of *these specific patterns*"
       (the gain itself is the absence of these patterns; the
        invariant does not claim absence of unrelated defects)

  "saturated" / "converged"
    → "checker returns 0 findings *against its current pattern set*;
       new finding-classes may exist beyond the checker's scope"

  "Final CI count: N"
    → "CI invariants at this checkpoint: N (point-in-time; expected
       to grow with future audit cycles)"

  "Statistically ≥X% likely natural" (from a small sample)
    → "the sample surfaced 0 issues; extrapolating to the unsampled
       remainder is not statistically justified from this sample
       size — the remainder is **unverified**"

  "every Japanese example is checked"
    → "every Japanese example *in the corpus as of this commit* is
       checked *for the specific patterns listed*"

  "covers all L2-error patterns" / "the top-14 L2 errors"
    → "covers the listed patterns" — name them, do not claim the
       list is exhaustive

  "comprehensive" / "exhaustive" (about coverage)
    → "broad-coverage *within the patterns named*"

PRACTICAL RULES:

  1. Every numeric finding count gets a denominator and a method.
     "115 flagged, 2 real" → "115 flagged across 6,309 sentences via
     <regex>, 2 real after triage, 113 FPs documented in FP-NN".

  2. Every "we caught X" claim names the pattern class. Patterns
     are CATALOGED in this prompt (A1-A47, FP-1-FP-15); cite them
     by number.

  3. Every CI invariant description says "prevents re-introduction
     of <named patterns>", not "locks <abstract concept>".

  4. Every "0 findings" survives only if the prose immediately
     after says what was searched. If the reader has to infer the
     scope, the prose is wrong.

  5. When a checker is added or extended, the audit-doc paragraph
     for that pass MUST note "this pattern was not in the prior
     run's scope" if it's new — so saturation deltas don't read as
     regressions.

  6. Phase-0 doesn't establish saturation against unknown patterns.
     It establishes that the CURRENT pattern set returns 0. Always
     write the qualifier.

  7. NEVER state a derived count (CI invariant total, corpus sizes)
     as a bare present-tense literal in a LIVING doc (spec, README,
     prompts, sync-map, self-host guide, CLAUDE.md). The count is a
     fact the deriving script computes on every run
     (`tools/check_content_integrity.py` for invariants; JA-107 /
     JA-115 for corpus sizes) — point to it ("the script reports the
     live count") or give a dated checkpoint ("171 at the 2026-05-29
     checkpoint"). A bare "NN invariants" in a living doc rots
     silently because nobody re-greps every doc when invariant N+1
     lands; the same fact then disagrees across a dozen surfaces.
     Point-in-time records (CHANGELOG, dated audit reports,
     version-stamped baselines, this brief's session logs) are
     exempt — a dated number there is a correct historical snapshot.
     The Phase-0 invariant-count drift scan in N5Improvement.txt
     mechanically enforces this against the living-doc set
     (procedure manual F.46.6).

Failure mode being prevented: an exam, a native reviewer, or a
learner finds a defect that the audit docs implied couldn't exist
("you said it was complete!"). The fix is qualified writing, not
qualified work — the work itself is honest; only the prose drifts.

A63. JA-91 + JA-94 final unblock — baseline-allowlist pattern for
     invariants that can't reach 0 false-positives mechanically.
     (Methodology — added 2026-05-17, AUDIT-COVERAGE Part 19.)

Two invariants from the JA-91..95 reserved range had been
partial-promoted then deferred because their detector mechanically
surfaced findings that mixed legitimate corpus structure with
genuine contamination:
  - JA-91 (cross-pattern explanation_en similarity ≥0.85) surfaced
    43 pairs — all hand-classifiable as legitimate cross-coverage
    (DUPLICATE_PATTERN, CROSS_REFERENCE, ALTERNATIVE_VARIANT, SUBSET).
  - JA-94 (every grammar example contains ≥1 structural marker
    from its parent pattern) surfaced 14 failing examples after the
    markers catalog reached 99.2% mechanical coverage — each a
    BUG-006-CANDIDATE (wrong example doesn't demonstrate parent
    pattern).

The unblock pattern: snapshot current findings into a baseline
allowlist JSON, classify each with a per-entry rationale note, and
trip CI ONLY on NEW findings beyond the baseline. Same pattern
established by JA-67 (Density-3 below-floor count locked at 24);
the JA-91 + JA-94 close-outs propagate it to two more invariant
classes.

When this pattern is appropriate:
  (a) The detector has 0 false-negatives against its target class
      but surfaces a known finite set of legitimate cases that
      can't be mechanically distinguished from genuine bugs.
  (b) Each baseline entry can be classified with a rationale note
      explaining WHY it's allowlisted (so a future audit cycle
      can re-evaluate).
  (c) The baseline file lives at `data/_jaNN_baseline.json` with
      a `_meta` block (purpose, classification_legend,
      snapshot_date, next_review_trigger).
  (d) The invariant's failure message tells maintainers HOW to
      add a new entry (add to baseline with classification OR
      fix the underlying content).

When NOT to use baseline-allowlist:
  - The detector has false-positives (surfacing actual non-bugs).
    Fix the detector first.
  - The class of legitimate cases is unbounded / growing rapidly.
    Strict closed-enum or per-rule check is better.
  - The baseline would carry >100 entries. That's a corpus-quality
    signal — the invariant itself is too strict and needs a
    refinement, not allowlisting at scale.

A67. Paper-question grammarPatternId mis-tag scan (PAPER-001).
     (Audit category — added 2026-05-18, AUDIT-COVERAGE Part 24.)

For every Mondai 1 paper question (data/papers/bunpou/paper-*.json)
whose `correctIndex` resolves to a single Japanese particle, the
`grammarPatternId` field MUST reference the canonical n5-NNN
pattern for that particle. Mismatches indicate an early auto-
tag pass that assigned default-tag (e.g., n5-013 = も) regardless
of the actual answer particle. The drift is silent at quiz time
(question plays correctly) but breaks study-plan grouping,
pattern-frequency analytics, and "review weak particles"
recommendation.

Canonical particle ↔ pattern_id map (read from grammar.json
Particles category, single-char pattern field):

  は → n5-002    が → n5-003    を → n5-004    に → n5-005
  へ → n5-006    で → n5-007    と → n5-008    から → n5-009
  まで → n5-010   や → n5-011    も → n5-013    か → n5-023
  ね → n5-025    よ → n5-026    の → n5-028    だけ → n5-033
  ぐらい/くらい → n5-035        ごろ → n5-036    など → n5-037
  ずつ → n5-038    より → n5-095 (comparison)

For non-particle Mondai 1 questions (verb/adj/copula form,
counter, te-form, comparison construction, etc.), per-stem
context-based manual mapping is required.

For Mondai 2 sentence-ordering and Mondai 3 paragraph-gap, tag
by the central structural pattern OR the specific particle/form
filling the blank — whichever the question primarily tests.

Provenance: set grammarPatternId_provenance =
"rule_based_correctanswer_<YYYY_MM_DD>".

CI invariant: JA-120 (paper bunpou Mondai-1 grammarPatternId
matches canonical particle pattern, PAPER-001 drift guard,
2026-05-18).

pattern_id alignment *for Mondai 1 questions where
correctIndex resolves to a single particle in the canonical
map*. Non-particle Q (verb/adj/copula form) and Mondai 2/3
require manual review; A67 does not auto-verify those.

A68. Paper-rationale meta-fix-history scan (PAPER-003).
     (Audit category — added 2026-05-18, AUDIT-COVERAGE Part 24.)

For every paper question, the learner-facing `rationale` and
`rationale_hi` fields MUST NOT contain commit-message-style
meta-fix history. Substring scan triggers on:

  - auto_inferred, previously tagged, prior version was
  - Stem now anchored, Stem now includes
  - replaces colloquial, replaces ので per
  - the original option, was dropped because,
    replaced with, patched to, fix:

These phrases describe corpus maintenance — appropriate for
commit messages, inappropriate for the post-answer screen
that learners actually see.

keep only the learner-facing concept explanation. Move audit-

rationale_revision_note field. KEEP distractor-analysis

learner value.

commit-message-style meta-fix history, PAPER-003 drift guard,
2026-05-18).

Bounded-coverage phrasing: A68 prevents re-introduction of
*these specific bad-phrase substrings*. Stylistically poor or
verbose rationales that don't contain the trigger phrases pass.

A69. Paper-rationale_hi natural-Hindi scan (PAPER-004).
     (Audit category — added 2026-05-18, AUDIT-COVERAGE Part 24.)

For every paper question, the learner-facing `rationale_hi`
field MUST be natural Hindi — not word-by-word literal
translation of `rationale_en`. Substring scan triggers on:

  - Apostrophe-s possessive: 's घर, 's दिन, दोस्त's,
    माता's — non-existent in Devanagari grammar
  - English contractions inline: मैं'm, मैं'have, मैं'll,
    मैं't — half-translated artifacts
  - Mojibake: यहाँre, वहाँre, Iहाँ, o'घड़ी, o'क्लॉक
    (English apostrophe + Hindi script glued together)
  - Untranslated English filler: " yet,", "है yet", " lot ",
    "I am ", " have जाना", " have रहा"

Fix protocol: source from rationale_en (verified correct),
translate naturally into Hindi. Test: "Would a Hindi-speaking
N5 learner read this fluently?" Keep Japanese tokens as-is
(do not transliterate to Devanagari). Particle names stay as
Japanese characters. Set
rationale_hi_provenance = "native_reviewed_<YYYY_MM_DD>".

CRITICAL anti-pattern: do NOT translate from the broken
rationale_hi back into clean Hindi. The broken Hindi may itself
be a wrong translation (different sentence than the question's
actual stem). Always source from rationale_en + verify against
the actual stem + correct answer + choices.

CI invariant: JA-122 (paper rationale_hi free of English-
pattern fragments — apostrophe-s / contractions / mojibake,
PAPER-004 drift guard, 2026-05-18).

Bounded-coverage phrasing: A69 catches *automated English-
fragment detection* — the trigger substring set. Legitimate
technical fragments (e.g., "sub-が-suki", "X-jin") and
Japanese-token + Romanized particle references remain by
design. Stylistically-stiff-but-grammatical Hindi passes.

  5. Corpus discovery JSON at /Nx/data/index.json (per-file

  6. LLM-discovery TXT at /llms.txt (root) + /Nx/llms.txt

A71. Register-variant vs grammar-error distinction — 6 defect
     classes (D1..D6) per REG-001 close-out. (Audit category —
     added 2026-05-18, AUDIT-COVERAGE Part 25.)

A grammatical register CHOICE between two correct forms (e.g.,
だれ vs どなた, けど vs けれど, わかってる vs わかります) must NOT
be framed as WRONG/RIGHT in wrong_corrected_pair. Both forms are
grammatical; the choice is register, not correctness. The right
schema is register_variant nested in common_mistakes with
form_a / form_b / label_a / label_b fields.

Six defect classes (per procedure manual §F.32.1):

  D1 — WRONG/RIGHT framing on a register choice
  D2 — Conflated semantics in "alternatives" list (e.g. identity
       vs description presented as register equivalents)
  D3 — Formality vs elevation conflation (sentence-level
       formality ≠ referent-elevation 尊敬)
  D4 — Out-of-Nx-scope item taught as canonical (no scope_note)
  D5 — Kana form of whitelist kanji (JA-100 violation)
  D6 — Self-contradicting annotation: ✗ line annotated as
       appropriate to a register

The register_variant schema:

  kind: register_variant
  form_a, form_b: both grammatical forms
  label_a, label_b: register descriptors (neutral / honorific /
                    casual / formal / etc.)
  why: explanation
  category: register
  scope_note: optional, flag out-of-Nx-scope

CI invariant: JA-127 (REG-001 D6 self-contradiction guard) —
scans wrong_corrected_pair entries with error_category=register
for parentheticals like "(formal)" / "(in casual conversation)"
in the wrong-field.

Sweep procedure (D1..D6 across the whole corpus): documented in
procedure manual §F.32.4. SWEEP-6 (D6 class) is the easiest to
automate via JA-127. SWEEP-1 surfaces candidates but each needs
per-entry native-speaker triage. SWEEP-2..5 deferred to native-
speaker review sessions.

REG-001 close-out (2026-05-18) — fixed 6 entries:
n5-046.wcp[1] (the original REG-001 target) +
n5-097.wcp[1] / n5-102.wcp[2] / n5-127.wcp[0] / n5-173.wcp[1] /
n5-179.wcp[1] (D6 hits caught by JA-127 on first run).

SWEEP-1 candidate report at
docs/REG-001-SWEEP-1-candidates_2026_05_18.md surfaces 84
remaining entries for native-speaker triage as REG-002..NN
follow-up filings.

Bounded-coverage phrasing: A71 + JA-127 catch the D6 marker-
phrase set. D1..D5 classes need per-entry review. A creatively
phrased D6 violation without these markers slips past.

A72. Paper-question schema-discipline — 3 durable classes
     (DOKKAI-001..003 close-out). (Audit category — added
     2026-05-18, AUDIT-COVERAGE Part 26.)

For every paper-bank file (data/papers/<category>/*.json), three
schema-discipline classes must hold. Each maps to a CI invariant
introduced in this batch.

Class A — Single source of truth for passages (CI: JA-128)
  Paper questions MUST NOT carry passage_text. The canonical text
  lives in passages[].text at the paper top-level. Questions
  reference passages via passage_label foreign key. Renderer joins
  at display time. Catches the redundancy-then-drift class where
  the same passage is stored in 2 places and one copy gets a fix
  the other doesn't (12 of 102 dokkai questions had drifted via a
  leading "> " markdown-blockquote prefix on one copy but not the
  other).

  When a paper-bank exists WITHOUT passages[] (e.g., bunpou
  Mondai-3 paragraph gap-fills that only have passage_text per
  question), the fix is to CREATE passages[] from the unique
  passage_text values + their passage_label keys, then drop
  passage_text. The bunpou/paper-7.json file went through this
  migration in the 2026-05-18 close-out.

Class B — English-fragment temporal markers in rationale_hi
  (CI: JA-129, extends JA-122)
  Paper rationale_hi MUST be free of untranslated English temporal
  or quantity markers. Trigger set: " ago ", " ago.", " ago,",
  " ago)", " ago]", " yet ", " yet.", " yet,", " yet)", " lot ",
  " lot.", " lot,". Carry-over from word-by-word translation where
  the Hindi sentence-order pattern made these English words fall
  through untranslated. Rewrite with target-language idiom: "पहले"
  for ago/before, "अभी तक नहीं" for "not yet", etc.

  Conservative: " before " and " then " are NOT in the trigger
  set because they can appear in legitimate Romanized technical
  glossing (e.g., grammatical-pattern references). False-positive
  risk on the trigger set is more harmful than letting through a
  few more cases that JA-122 / native review would catch.

Class C — Schema-shape: explicit-null vs missing-key (CI: JA-130)
  Every paper question MUST have grammarPatternId as a key. When
  the question doesn't test a specific grammar pattern (dokkai
  comprehension / goi vocabulary / moji orthography), set value to
  null AND set provenance to a typed not_applicable_<reason> value:

    - dokkai comprehension: "not_applicable_comprehension"
    - goi vocabulary: "not_applicable_vocab"
    - moji orthography: "not_applicable_orthography"

  Distinguishes "not yet assigned" from "intentionally absent —
  not applicable to this question type". Same always-a-key-
  sometimes-null pattern as VOCAB-002 counter-field (BUG-015).

  - "JA-128 prevents *passage_text on paper questions*" — not

    untranslated English". JA-122 covers apostrophe-s + mojibake;

  - "JA-130 enforces *presence + documented null*" — not

A75. Mixed-script mojibake + off-by-one rationale_hi shift +
     extended fix-history strip (GOI-004..006 close-out).
     (Audit category — added 2026-05-21, AUDIT-COVERAGE Part 33.)

Three durable rationale-content defect classes from the second
goi-corpus sweep iteration. Each had a sibling instance elsewhere
in the corpus that the original single-fix sweep missed — the
operational lesson is "horizontal-deployment sweep is part of the
fix commit, not a follow-up." CI-enforced via JA-137 + JA-139 +
JA-121 trigger extension. Combines with A74 to form a 7-invariant
family on paper-question rationale fields.

Class A — Mixed-script Devanagari-inside-kana mojibake (CI: JA-139)
  A rationale_hi token mixes scripts inside a single word: kana
  あ + Devanagari ma + Devanagari ī as one unit (「あमारी」), or
  kana ぐら + Devanagari ī (「ぐらि」). Likely cause: an earlier
  search-and-replace or transliteration pass substituted kana
  with closest-glyph Devanagari without script-boundary check.

  GOI-006 example: goi-7.4 rationale_hi had 「あमारी ありません」
  where the kana 「あまく」 was meant. Result: invalid Japanese,
  invalid Hindi, garbled the polite-negative paraphrase point.

  Horizontal-deployment finding: the sharpened JA-139 detector,
  run corpus-wide, surfaced 2 MORE instances in dokkai-2.11
  (「一時間ぐらि」 → 「一時間ぐらい」) and dokkai-3.4 (「あमारी
  上手では」 → 「あまり 上手では」) that the goi-only sweep missed.
  All 3 fixed in the same batch as BUG-135.

  Detector: regex `[ぁ-ゖァ-ヺ一-鿿][ऀ-ॣ०-ॿ]` — Devanagari
  letter immediately following a kana/CJK character. Exclusions:
  danda ।  (U+0964) and double-danda ॥ (U+0965), which are
  legitimate sentence-end punctuation; hyphen-separated cross-
  script terms like 「い-विशेषण」.

Class B — Off-by-one rationale_hi shift across consecutive Qs (CI: JA-137)
  Two consecutive questions have their rationale_hi shifted by
  one: question N carries (N+1)'s rationale_hi; (N+1) carries
  (N+2)'s. English rationale is correct on both; only Hindi shifted.
  Hard to catch with a strict token-overlap detector (21% FP rate
  on existing corpus from polite/dictionary form variation), so the
  detector targets the NARROW shift signal: rationale_hi has 0
  overlap with own stem AND ≥2 overlap with next-Q's stem.

  GOI-004 example: goi-7.6 stem about ゆうがた/夕方 carries goi-7.7's
  「話すのが じょうず」 rationale_hi; goi-7.7 stem about 話すのが
  じょうず carries goi-7.8's 「しゅくだいを 出す」 rationale_hi.
  goi-7.8 itself is correct.

  Detector lifts the "narrow signal" idea: any same-question rationale_hi
  that ZERO-overlaps with its own stem AND TWO-PLUS overlaps with next-
  question's stem is flagged. Rejected: a strict broad-overlap detector
  with the same coverage produced ~100 false positives from polite/
  dictionary form variation. Sharper detector → cleaner CI gate.

Class C — Extended fix-history / version-references / replacement-history (CI: JA-121 extended)
  Extension of A74 Class B (PAPER-003 / GOI-002/003). 7 more rationale
  fields surfaced in goi sweep iteration 2 with phrases like:
    - "replaces the prior" / "replaces the previous"
    - "previous version" / "prior version"
    - "Strict-N5:" + "in v1." + "policy applied at"
    - "no longer appears" + "Note: kept in kana since 私 is not in..."
    - Hindi "पिछले संस्करण" / "पुराने" / "की जगह लेता"

  JA-121 trigger set extended 2026-05-21 with these 11 phrases.
  No new JA-NN minted — the existing detector's name and intent

Four durable defect classes from the moji-paper content review.
Combines with A67 (PAPER-001 grammarPatternId mis-tag) + A72 (paper-

Class A — Per-mondai stem-emphasis convention split (CI: JA-140)
  A subsection of one corpus uses HTML `<u>...</u>` for emphasis while
  another subsection uses markdown `__...__`, with no documented
  contract declaring the split. Renderer fragility: an HTML-only
  renderer displays markdown literally as underscores; a markdown-
  only renderer leaves HTML tags as raw text. Either way the emphasis
  fails on the half that doesn't match the renderer's rule-set.

  MOJI-001 example: moji Mondai 1 (50 questions) used `<u>X</u>`;
  moji Mondai 2 (50 questions) used `__X__`; paper-4 mixed both
  within one file at the Mondai 1→2 boundary. Field name is
  `stem_html` (implying HTML rendering), but half the corpus used
  markdown.

  Resolution pattern: pick ONE convention based on the rendering
  target. For a web UI with `stem_html`-named fields, HTML `<u>X</u>`
  is the right choice. Convert the other half in one atomic pass.

  Detector: regex `__[^_]+__` in any moji `stem_html`. Trip = at
  least one moji question still uses markdown emphasis.

Class B — auto_inferred grammarPatternId on orthography questions (CI: JA-141)
  Auto-inference of `grammarPatternId` picks up surface-token similarity
  without semantic understanding. On grammar tests this is usually
  sound. On ORTHOGRAPHY tests (moji = kanji-reading / kana-to-kanji
  conversion), the kana particles inside the stem (も in こども, は in
  今日, に in 北 に あります) are NOT what the question tests — but
  auto-inferrence still produces n5-013/n5-117/n5-067 etc. tags.

  Same anti-pattern class as the n5-013 over-misuse fixed at
  PAPER-001 in the bunpou paper sweep. The unique signal for moji:
  the question's *correct-answer selection* never hinges on a
  particle decision — it hinges on a kanji-reading decision. So
  `grammarPatternId` should be null + `not_applicable_orthography`
  in nearly all cases.

  MOJI-002 example: 28 of 100 moji questions had spurious
  `grammarPatternId` values (n5-013, n5-117, n5-067, n5-078, n5-108,
  etc.) auto-inferred from incidental tokens. None of the 28 actually
  tested the inferred grammar pattern.

  Resolution pattern: bulk-scrub the entire orthography category to
  null + `not_applicable_orthography`. If any question is later found
  to legitimately test a pattern, restore individually with manual
  review (forbid `auto_inferred` provenance via CI).

  Detector: moji-category question with grammarPatternId non-null
  AND `grammarPatternId_provenance == "auto_inferred"`. Trip = at
  least one such question exists.

Class C — Word-by-word HI rendering of EN verb constructions (CI: JA-142)
  Translation pass renders English verb constructions word-by-word
  into Hindi when no direct cognate exists. Symptoms:
    EN: "X has reading Y in Z"
    HI: "X के पास है पढ़ते हुए Y में Z" — grammatically broken.
  Natural Hindi: "X का पठन Z में Y है".

  Same defect class as DOKKAI-002 (`एक महीना ago`), DOKKAI-004
  (`आना-जाना by ट्रेन`), PAPER-004 fragment scan (`यहाँre`, `o'घड़ी`).
  Each fix adds a substring-trigger to a corpus-wide regression
  scanner. Per-defect-class trigger phrase:
    JA-122 (PAPER-004): `'s घर`, `यहाँre`, `o'क्लॉक`, etc.
    JA-129 (DOKKAI-002): ` ago `, ` ago.`, ` yet `, ` lot `, etc.
    JA-142 (MOJI-005): `के पास है पढ़ते हुए`

  MOJI-005 example: moji-2.1 + moji-2.2 both used the broken
  construction. Rewrite pattern: replace with natural-Hindi `X का
  पठन Y है` syntax.

Class D — Cross-language content-coverage truncation (CI: JA-143)
  Translation pass produces a HI rationale that says LESS than the
  EN counterpart. Symptoms:
    EN (343c): "...The other forms 起ちます/経ちます/建ちます are real
                 Japanese verbs ... for N5 the 立 form is the only
                 correct match."
    HI (250c): "...अन्य रूप 起ちます/經ちます/建ちます भी असली ... [STOP]"
                  — drops the "only correct match" conclusion.

  This is content-coverage parity, NOT translation-quality. The HI
  reader is left ambiguous on the question's pedagogical takeaway
  while the EN reader gets a definitive answer.

  Detector: for any question with rationale ≥ 80 chars AND
  rationale_hi ≥ 40 chars, the HI/EN length ratio must be 0.6 ≤ r ≤ 2.0.
  (0.6 floor accounts for HI's typical 1.3× expansion vs EN; 2.0
  ceiling catches the inverse where EN dropped content. Below 0.6
  = HI truncated; above 2.0 = EN truncated.)

  MOJI-006 example: moji-7.2 was at 250c HI / 343c EN (ratio 0.73,
  borderline but acceptable on raw ratio; the truncation was on the
  CONCLUSION sentence specifically). The threshold was set at 0.6
  after analyzing pre-existing distribution; tighter than 0.6 would
  false-positive on legitimately-concise HI rationales.

  Same-class follow-ups discovered when JA-143 first ran:

Class A - Governance-doc stale-state class (CI: governance review;
         convention via Document status header)

  Pattern. Hand-maintained README / governance docs claim
  numerical state (counts, alignment ratios, deletion claims)
  that drift from reality as the corpus moves through batch
  cleanups. The docs were authored at a snapshot point (e.g.,
  v1.12.8) but the corpus has since moved (v1.15.5) without
  doc updates.

  N5 instances (8 in one audit pass):
    - DOCS-VOCAB-001: 1041→995 entry-count drift (46-entry stale)
    - DOCS-VOCAB-004: math 1041-969=72 surplus enumerated to
      only 17; other 55 hand-waved
    - DOCS-KANJI-001: false "canonically 103 per JLPT.jp"
      authority citation (third-party reconstruction misattributed
      to JLPT.jp's official scope)

  Resolution pattern: install a "Document status" header
  convention on every governance doc:

    Document status:
    - Last verified against corpus: YYYY-MM-DD
    - Corpus version at verification: vX.Y.Z

  Stale drift becomes visible at a glance. Future readers + audit
  reviewers can immediately see when the doc was last reconciled.

  Detector: governance-doc audits scan for the header presence.
  Could be wired as CI invariant if needed (currently convention).

Class B - Broken cross-file ref class (CI: extension of JA-117 / JA-82)

  Pattern. README / spec claims a directory/file was deleted but

  Resolution: either (a) restore the missing target, (b) update
  the broken refs, or (c) downgrade to honest tombstones
  (`"(authored in-place; was X before Y date)"`). N5 went with (c)

  Detector: filesystem-resolve every path-string in every

  see_also) + JA-109 (procedure-manual / prompts script refs).

  paths (heuristic: contains `/`, ends in known extension).

Class C - False-authority citation class (no CI; manual review)

  actually publish what's claimed. The cited number circulates in

  N5 instance: DOCS-KANJI-001 - "canonically 103 kanji per
  JLPT.jp" but JLPT.jp's own FAQ says they don't publish kanji

  Detector: hard to automate (requires semantic verification).
  Treat as a per-audit manual check; flag any "canonically per",

Class D - Underspecified-format class (CI: regex-validation pattern)

  Pattern. Governance doc says a field is "optional date for X"
  or "format: see tooling" without specifying the canonical

  contributors enter free-form values ("Q3 2026", "next release",
  "2026-08", "August 2026" all valid by the prose; none valid by
  the parser).

  N5 instance: DOCS-KANJI-004 - REVIEW_DATE field format
  unspecified. Fixed by specifying ISO 8601 + wiring JA-144

  Resolution: for every optional/free-form field in a governance
  doc, specify the canonical format (ISO 8601 for dates, RFC 3987
  for URIs, ...). Add a CI invariant that regex-validates the
  format. Skip values inside HTML comment blocks

  Pattern wiring: `^- FIELD: \d{4}-\d{2}-\d{2}$` style match

Class E - Indefinite-bootstrapping class (CI: convention via exit criteria)

  Pattern. Governance doc references a "bootstrapping mode" or
  "pending state" without exit criteria. The invariant or feature

  N5 instance: DOCS-KANJI-003 - JA-25 in bootstrapping mode

Class F - Orphaned-CI class (CI: workflow location verification)

  Pattern. CI workflow files authored at the wrong directory
  location are silently never executed. GitHub Actions only reads
  `.github/workflows/` at REPO ROOT. Files at `N5/.github/workflows/`,
  `subproject/.github/workflows/`, etc. are silently inactive.

  N5 instance: 5 workflow files (browserstack / content-integrity /
  lighthouse / playwright / regen-llm-surfaces) at
  `N5/.github/workflows/` had been defined-but-never-executed since
  authoring. Verified via `gh api repos/.../actions/workflows`:
  only Dependabot Updates + pages-build-deployment were
  registered pre-fix.

  Symptoms (what indicates the orphan class):
    - `gh workflow list` shows fewer workflows than the local
      .github/workflows count
    - `gh api repos/.../actions/workflows` shows only Dependabot +
      Pages defaults
    - Workflows-defined-locally never appear in recent run history
    - Recently-introduced check failures (CSS drift, data
      integrity, etc.) never surface — because the workflow that
      would catch them isn't actually running

  Resolution: `git mv subproject/.github/workflows/* .github/workflows/`
  + add `defaults: run: working-directory: subproject` per job +
  update branch trigger to match the repo's default branch (master
  vs main).

  Detector: every audit cycle, verify `gh workflow list` matches
  `find . -name "*.yml" -path "*/.github/workflows/*"`. Mismatch =
  orphaned workflows.

  Once activated, expect a backlog. The N5 instance surfaced:
    - 37 CRLF-vs-LF size_bytes drift violations (cross-platform
      metadata class)
    - last_modified mtime drift on every push (CI metadata
      ephemeral-fields class)
    - generated_at timestamp drift on every push (same class)
    - 1 reference to a deleted KB-era script
    - 112 design-system violations across D-1..D-6 (pre-existing
      backlog hidden by orphan)

  These are normal "previously-inactive checks activate" outcomes,
  not regressions. Plan for backlog payment.

Class G - CI-metadata ephemeral-fields class (CI: drift-guard via field removal)

  Pattern. Build scripts that generate artifacts (manifests, index
  files) record per-regen timestamps. CI regenerates → records
  ITS timestamp → diff fails the "no drift" check even when
  content didn't change. Result: every push spuriously fails
  drift-guard workflows.

  N5 instance: `data/index.json` recorded
    - per-entry `last_modified` (mtime from filesystem)
    - top-level `_meta.generated_at` (UTC now at regen)

  Both changed every regen → CI failed on every push regardless
  of content changes.

  Resolution: drop ephemeral fields from generated artifacts.
  Build-tag belongs in version.json (single source of truth);
  not in every derived artifact. Generator identity can stay
  (`_meta.generator`) since the script path is stable.

  Detector: a CI "regen produces no diff" check is itself the
  detector. Any field that fails this check on every push is an
  ephemeral-field candidate for removal.

Class H - Cross-platform line-ending class (CI: LF-normalize at compute time)

  Pattern. Build scripts on Windows compute byte sizes via
  `os.path.getsize()` which returns CRLF-bloated counts. CI on
  Linux compares against LF-only file sizes. Mismatch ~1-3% per
  file across the corpus.

  N5 instance: `data/index.json.size_bytes` recorded CRLF sizes
  on Windows-authored regens. Linux CI saw LF sizes. 37
  violations on first real CI run.

  Resolution: LF-normalize when computing canonical sizes:
    `len(open(path, 'rb').read().replace(b'\\r\\n', b'\\n'))`
  Apply BOTH at the build script (recording the size) AND at the
  CI check (computing the actual size). Both ends must agree on
  canonical (LF) representation.

  Detector: any size-tracking field that diffs cross-platform
  is a candidate. The build script + check function must both
  normalize.

A78. CI-recovery triage - test-side and product-side discoveries
     when the Playwright suite first ran green
     (2026-05-21 CI-recovery batch — 6 durable classes from
     post-timeout-fix triage of 65 pre-existing failures).
     (Audit category - added 2026-05-21, AUDIT-COVERAGE Part 36.)
============================================================

Six durable classes from the 2026-05-21 CI-recovery triage. When
the Playwright suite first ran green (after parallelisation +
video-off + 15-min timeout), the cancellations had been masking 65
failures across 6 distinct classes. This entry generalises the
discoveries so the patterns are detectable by future audits.

Class A - CI-timeout-masking-failures class (operational)

  Pattern. A long-running CI suite hits the workflow timeout cap
  and gets cancelled. The cancellation prevents the test reporter
  from printing failure summaries, so the CI badge says "cancelled"
  instead of showing the actual failure breakdown. Repeated
  cancellations look like an infrastructure problem when they're
  actually concealing 50+ assertion failures.

  N5 instance. Playwright suite cancelled at 8m22s / 12m21s /
  15m17s on three successive runs. The actual cost wasn't in setup
  (cache-restored browsers took 25s) - it was workers: 1 that
  serialised 120 test instances. Parallelising to workers: 2
  collapsed runtime to 2m33s and surfaced 65 unique failures.

  Detector. When CI is consistently "cancelled" rather than
  "failed": read the actual log via `gh run view <id> --log-failed`,
  get the per-step timing breakdown, then parallelise BEFORE
  bumping the timeout.

Class B - Stale test assertions when UI evolves class

  Pattern. When the UI is restructured (elements removed, text
  changed, layout collapsed), tests against those affordances become
  stale but typically don't fail loudly until the test suite runs
  end-to-end.

  N5 instances. ~15 stale tests: `.syllabus-title` /
  `.syllabus-trust-band` / `.locale-chip` (removed); "Start sitting"
  → "Start full mock test" (copy change); 177 → 178 grammar
  patterns / 30 → 54 reading / 30 → 50 listening (count drift);
  `button.length-btn` → `<select id="test-length">` (UI redesign).

  Resolution. Replace hardcoded counts with `fetch('data/version
  .json')` reads at test runtime. For removed UI, either skip
  with a git-history reference or rewrite for the replacement.
  Prefer regex match for product-marketing-controlled copy.

  Detector. After ANY UI restructure: grep `tests/` for class
  names + copy strings touched. Horizontal-deployment sweep
  extends to test artifacts in the same commit as the UI change.

Class C - First-run onboarding bypass for tests class

  Pattern. When the app has a "first-run experience" gate
  (redirect on no-history / no-streak / no-results), every CI test
  hits it because Playwright's fresh-context browsers have empty
  localStorage. Tests asserting against the home DOM find a
  diagnostic-page DOM instead.

  N5 instance. IMP-044 (2026-05-11) added first-run onboarding:
  hash-less visits with no history redirect to #/diagnostic. Every
  test loading `/` failed because the page title showed "JLPT N5
  placement diagnostic" not the home title. Affected ~12 tests
  across 3 spec files.

  Resolution. Add a global test.beforeEach that sets the
  onboarding sentinel via addInitScript before navigation:

    test.beforeEach(async ({ page }) => {
      await page.addInitScript(() => {
        try { localStorage.setItem(SENTINEL_KEY, '1'); } catch {}
      });
    });

  Detector. When a fresh-context CI run produces "title mismatch"
  or "element not found" failures concentrated on hash-less routes,
  check for first-run redirect logic.

Class D - Rule-order bugs in priority chains class

  Pattern. A recommender / decision engine with rules in a
  priority chain has a too-permissive catch-all that dominates
  lower-priority specific rules.

  N5 instance. Pedagogy recommender's R-13 ("catch-all returning
  user gets Open Learn") had condition `if (signal.isReturning)` -
  too broad - and dispatched BEFORE R-14 ("mock-paper ready",
  grammar≥60% AND kanji≥50%). R-14 was dead code for any returning
  user.

  Resolution. Audit every rule chain for catch-all conditions.
  Document explicitly which rule is "the catch-all" - one per
  chain, placed at the END of dispatch. Add positive + tie-break
  tests for EVERY rule.

  Detector. For any module with a "rule_id" / "priority" / "rules
  array" pattern, audit the dispatch loop: does the most-permissive
  condition appear before more-specific ones? Catch-alls go last.

Class E - Color-contrast on branded headers class (CI: axe-core)

  Pattern. A design system ships a "muted text" color calibrated
  for white / default-surface backgrounds. When used inside a
  branded header band (non-white bg), the contrast ratio fails
  WCAG AA.

  N5 instances. `--color-text-muted: #6F6D66` on tea-green
  `--header-bg: #cfd8b5` = 3.48 contrast (fails). Used in
  `.primary-nav a`, `.app-header .icon-btn`. Parallel case:
  `--color-text-faint: #9A968C` on white footer = 2.95 contrast.
  axe-core flagged 408+ violation instances on the homepage alone.

  Resolution. Introduce a `--color-text-on-<surface>` token per
  non-white branded surface. Use the surface-specific token in
  every selector living on that surface. Keep the original
  muted/faint tokens for white-bg contexts.

  Detector. axe-core color-contrast check (already part of P0
  smoke). Pre-emptive guard: for each new non-white branded
  background, audit every text-color rule that lives on top of it.

Class F - Cross-platform snapshot baselines class

  Pattern. Visual-regression tests with screenshot baselines tag
  each baseline with the OS (`-win32.png`, `-linux.png`,
  `-darwin.png`). If the dev box that captures the baselines runs
  Windows but CI runs Linux, the suite hits a 100% miss rate.

  N5 instance. 76 committed PNGs all `-win32.png`; CI Linux
  requests `-linux.png` → 38 unique "snapshot doesn't exist"
  failures since suite was wired 2026-05-03.

  Resolution. Three options in order of effort:
    (a) Skip on CI: `test.skip(!!process.env.CI, ...)`. Local
        dev still gets diffing. Quick unblock.
    (b) Workflow-dispatch regenerate: add `update-snapshots` input,
        run `--update-snapshots`, upload artifact, commit.
    (c) Per-OS baselines committed: run on all supported platforms,
        commit all baselines.

  Detector. Once a visual-regression suite is wired: grep
  `tests/**/*-snapshots/` for baselines; if all are tagged with a
  single OS and CI runs a different OS, every diff will miss.

Operational rule §A78.7 - the discovery-cascade rule

  When an infra fix unblocks visibility (CI timeout fix, log-level
  fix, infrastructure migration), treat the next N hours as
  observation time, not fix time. Capture the full failure list,
  bucket by class (test-side vs product-side; new vs pre-existing),
  stack-rank by fix cost, commit in revertable batches with
  per-batch scopes. After every batch, re-read the CI log - new
  failures may surface as old ones get out of the way. The final
  batch is doc propagation per Rule 4 + bug-sheet registration per
  Rule 5.

before KnowledgeBank/ merge into data/ + docs/N5-syllabus-methodology.md
on 2026-05-14)" in every paper-file across all 4 categories.

Anti-pattern. When a directory is deleted as part of a refactor, every
field that referenced that directory in prose either:
  - keeps the prose (and the directory name leaks into N28 files of
    metadata for years, including in CI greps / docs / search results
    that misclassify it as a current pointer), or
  - is replaced with a half-fix that breaks correctness (e.g., pointing
    source_file at a methodology doc that doesn't actually contain the
    sourced content; what DOCS-VOCAB-005's original bug spec proposed).

Canonical sentinel pattern (CI JA-145). For data fields that represent
provenance of authored-in-place content, define a literal canonical
sentinel string and a parallel resolvable-path option. The CI invariant
enforces: source_file in every paper file is EITHER
  (a) a path that resolves to an existing repo file, OR
  (b) the literal string "(authored in-place)".

Other values fail. The sentinel approach is honest (questions ARE
authored in-place), preserves the schema field (so downstream consumers
don't break), and lets future external-source papers populate the
field with a real path that JA-145 will verify resolves.

DOCS-VOCAB-005 specifics:
- Replaced 28 prose values across data/papers/{bunpou,dokkai,goi,moji}/
  paper-{1..7}.json with the literal sentinel.
- Wired JA-145 to lock the sentinel-or-path invariant.
- Closes the unaddressed half of DOCS-VOCAB-003, which had marked itself
  Fixed after only updating the README (case (a)) without touching the
  28 paper files (case (b)).
- Historical KB breadcrumb preserved in CHANGELOG + n5_vocab_whitelist_
  README.md + git history (commit 136abc4); no information lost.

Operational lesson — "Premature-close-without-fix detection":
DOCS-VOCAB-003 demonstrates how a multi-case bug can be incorrectly
closed by addressing only one case. The fix: in any bug that lists
"case (a) OR case (b)" resolution paths, the close-out must specify
which case was taken AND explicitly note the other case as either
resolved-in-this-batch or filed-as-follow-up. Marking the bug Fixed
without that disambiguation buries the unaddressed half.

Bounded-coverage phrasing:
  - "JA-145 catches *source_file values that are neither the literal
    sentinel '(authored in-place)' nor a resolvable repo path*" — does
    not catch a future case where source_file points at the wrong file
    (would resolve but be semantically wrong).
  - "Canonical sentinel pattern at *this one field*" — generalising to
    other authored-in-place fields would need separate JA-NN with the
    sentinel string each field uses.

A80. COVERAGE-GAP CLOSURE — type-confusion in string fields +
     doc-state-vs-code-state drift (2026-05-22 meta-audit batch).
     (Audit category — added 2026-05-22, AUDIT-COVERAGE Part 38.)
============================================================

Two coverage classes the existing 147 invariants weren't designed
to catch, surfaced by a meta-audit conversation rather than a
content bug. Generalizes the reactive→proactive CI-invariant-
authoring tension into a named audit category for future review.

Class A — Type-confusion in string fields (CI: JA-146)
  A spreadsheet column or JSON field is *typed* as "string" in the
  schema but *meant* to hold a specific shape (commit hash, ISO date,
  file path, URL, enum). The schema accepts any string, so type-
  checkers don't fire. Actual values drift from the intended shape
  via muscle-memory data entry, autocomplete suggestions, Excel
  auto-coercion to datetime, or simple typos that look plausible.

  N5 proof point: 150/155 Fixed rows in the xlsx bug-tracker had
  dates (99 as Excel-coerced datetime objects, 51 as YYYY-MM-DD
  strings) in the "Fix Commit" column. JA-118 (the existing "non-
  empty Fix Commit" check) passed all 155 because none were empty —
  the failure mode was wrong-shape-with-non-empty-content. JA-146
  now locks the shape (hash OR `<...>`-shaped sentinel).

  Operational rule (extends procedure-manual F.42.1): for every
  string field where the *intended* shape is narrower than "any
  string," author the shape-invariant in the same commit as the
  schema addition. Don't wait for a content bug to surface the drift.

Class B — Doc-state vs code-state drift (CI: advisory tool, not strict)
  Hand-curated documentation (TASKS.md, roadmap files, README counts,
  feature checklists) drifts silently from the actual codebase. When
  a feature ships, the maintainer must remember to flip the
  corresponding `[ ]` to `[x]`.

  N5 proof point: SVA-1.1 (footer privacy badge) and SVA-1.4 (Export
  Progress button) were both shipped weeks before being noticed in a
  TASKS.md review on 2026-05-22 — still `[ ]` despite the features
  being live.

  Advisory heuristic (tools/audit_tasks_md_against_codebase_2026_05_22.py):
  for each `- [ ]` item, extract keywords, grep js/css/locales/etc,
  score HIGH/MEDIUM/LOW. Surface HIGH/MEDIUM candidates for human
  review. NOT a strict CI gate — false positives expected; the
  heuristic gets ~70% recall at acceptable FP rate.

  Why advisory rather than enforcing: a strict rule would need LLM-
  grade matching between feature descriptions and code surfaces;
  beyond practical reach. The maintainer sweep closes the gap.

Bounded-coverage phrasing:
  - "JA-146 catches *the shape mismatch we surveyed (hash-or-
    sentinel)*" — does NOT catch a hash that's stale or points at the
    wrong commit.
  - "Advisory heuristic surfaces *keyword matches between TASKS.md and
    named code surfaces*" — does NOT catch features shipped under
    different keywords or in surfaces not scanned.
  - "Coverage expanded by 1 strict invariant + 1 advisory tool at
    this checkpoint" — does NOT imply universal corpus correctness.

When a previously-closed review document is re-pasted (the

already-closed. Use these buckets for re-paste-triage:

  STALE — claim was real against an earlier corpus snapshot; current
    data already shows the fix. Reject as a filing; note in commit
    message + audit-coverage that the verification ran.

  REAL — current data confirms the claim. File as new bug; apply
    fix.

FP-17. Aggressive norm vs strip-only norm divergence (BUG-A/BUG-H
       audit-cluster sweep, 2026-05-24)
       ============================================================
       SHAPE: A common_mistakes row appears as a duplicate of
       another row under aggressive norm = re.sub('[, . " ? ! \\s]+',
       '', s), but the two rows are distinct under strip-only
       equality. Similarly, a cm row with `wrong == right` under
       aggressive norm may differ under `.strip()`-only equality.
       The two norm functions are NOT interchangeable for audit
       purposes — they classify content differently.

       FALSE-POSITIVE TRIGGER: An auditor uses one norm consistently
       across all classifications and flags rows that pass under
       a stricter or more lenient norm than the one the dataset
       was designed for.

       Triage discipline:
         - Document which norm function each audit class uses.
           (BUG-A dedup: aggressive norm; BUG-H wrong-vs-right:
           strip-only.) Mismatched norms produce inconsistent counts.
         - When rewriting a row to resolve a BUG-H wrong==right
           finding, prefer wrong/right pairs that differ in
           SUBSTANTIVE ways (different particle, different
           conjugation) — not just spacing or punctuation — so the
           rewritten row survives BOTH norms.
         - For BUG-A dedup, the aggressive norm is correct (the
           user explicitly chose it to catch spacing-only twin
           rows). For BUG-H, .strip()-only is the user's stated
           criterion.

       Source: BUG-A + BUG-H audit-cluster sweep 2026-05-24; 3
       cm rows in n5-126, n5-155, n5-166 looked like wrong==right
       under aggressive norm but were actually distinct teaching
       content under strip-only.

FP-18. Cross-array category-vocabulary mismatch (JA-51 backfill,
       2026-05-24)
       ============================================================
       SHAPE: When code paths promote entries between arrays
       (e.g., wrong_corrected_pair -> common_mistakes as a JA-51
       backfill after BUG-A dedup), the source array's category
       vocabulary may NOT match the destination array's CI-invariant
       whitelist. grammar.json's wrong_corrected_pair uses
       `error_category` values like `lexicon`, `pragmatic`,
       `word_order`, `morphology` — none of which are in JA-51's
       valid set `{particle, verb_class, conjugation, register}`.

       FALSE-POSITIVE TRIGGER: A naive cross-array promotion path
       copies the source's category value verbatim, producing 24+
       JA-51 violations on what should be a clean dedup-with-
       backfill pass.

       Triage discipline:
         - Audit every cross-array promotion path for fields
           whose validity is enforced by a CI invariant.
         - Implement a CATEGORY_MAP at the promotion boundary

FP-23. Template-generated conjugation / collocation artifacts in
       auto-built example fields (BUG-266 batch J, 2026-06-04)
       ============================================================
       SHAPE: A field that was bulk-generated by a frame template
       ("<form> + ます", "<form> + ました", "<adj> + ほん/ひと/くるま",
       "今日は とても <adj>です", "えいがは <adj>でした", "<noun>を かう")
       contains entries that are MALFORMED Japanese or SEMANTIC
       nonsense — because the generator pasted the headword into a
       fixed frame without conjugating or checking sense.

       Two sub-classes seen in vocab.json particle_examples +
       examples:
         (a) MALFORMED CONJUGATION — the dictionary form has ます /
             ました directly appended: べんきょうするます, かすました,
             あるます, すむます. This is never valid; you conjugate
             the stem. Affected ALL 110 verbs (one per pos: godan
             /ichidan/irregular). Deterministically fixable with a
             verb-class-aware conjugator (う-row→い-row+ます; drop
             る+ます; する→します; 来る→来ます).
         (b) SEMANTIC-NONSENSE FRAME — a fixed example/collocation
             frame applied to an adjective or noun it can't pair
             with: 今日は とても 白い/まるい/ぬるいです (a day isn't
             white/round/lukewarm), えいがは <color/taste/size>でした
             ("the movie was yellow"), この りんごは うるさいです
             (an apple isn't noisy), あたらしい/たかい カタカナ
             (a writing system isn't new/expensive).

         - Sub-class (a) is OBJECTIVE — a malformed conjugation is
           wrong at any JLPT level. Fix it deterministically
           (conjugator), then add a JA-NN that compares each
           particle_example against the entry's OWN form+ます /
           form+ました so it can never false-positive on a correctly
           conjugated form (JA-178 is the BUG-266 instance).
         - Sub-class (b) needs sense judgment. The frame is valid
           for SOME headwords (今日は とても すずしいです = fine;
           この本は おもしろいです = fine) and nonsense for others.
           Use a conservative allowlist for the frame's valid
           semantic class (e.g. "今日は とても X" → weather/day-
           quality adjectives only) and REMOVE the rest; never
           fabricate a replacement you can't verify. Each entry
           must retain ≥1 example after removal (guard).
         - When a field is template-generated, audit the WHOLE
           field across the corpus — the bug is never one entry.
           BUG-266 cited 12; the real scope was 110 verbs + ~32
           nonsense sentences.

                (c) UNNATURAL PARTICLE COLLOCATION (naturalness, native-
             judgment) — the template seeded a particle+verb that is
             grammatical in isolation but wrong/unnatural for THAT
             headword: pronouns/nouns showing 「Xを しる」 where the
             natural verb is する / another verb (しごとを する, not
             しごとを しる); question words showing 「だれを しますか」

A94. BLANK-FRAME PART-OF-SPEECH AGREEMENT (added 2026-11-07)
     ============================================================
     Trigger: a language read of the finished N4 kanji book found two
     文脈規定 items that had passed every automated gate and several review
     rounds, because each OPTION reads fine on its own and the error only
     exists in the FRAME around the blank:
       - 「えんそくは とても（　　）でした」, options all い-adjectives:
         every option yields 「〜いでした」 (楽しいでした), ungrammatical.
       - 「とても（　　）人です」, key 親切: a な-adjective before a noun
         needs な (親切な人), so the keyed answer itself breaks the frame.
     RULE: substitute EACH of the four options into the blank and read the
     whole sentence. The frame must be grammatical for all four; only the
     meaning may rule distractors out. Highest-risk frames: blank + でした /
     だ / では (い-adjectives: 楽しいでした is wrong, the past is
     楽しかったです), blank + a noun (bare な-adjectives), and options that
     mix parts of speech. NOT a frame break: い-adjective + です or + でしょう
     (楽しいです, 強いです are correct) - flagging those is a false positive.
     FIX SHAPES: move the blank so it modifies a noun (「とても（　　）
     えんそくでした」), or print the options in the form the frame needs
     (親切な / しずかな). Never fix by changing only the key.
     Phase-0 check: tools/check_blank_frame_pos.py (validated 2026-11-07:
     214 blank items in N5 data/questions.json scanned, 0 violations; both
     N4 originals caught when run as a synthetic corpus). The check judges
     only options whose part of speech the corpus vocab lists, so a clean
     run is bounded to those; a manual read still owns the rest.
     Cross-ref: procedure-manual F.65; N5Improvement Phase-0 blank-frame
     part-of-speech agreement block; AUDIT-COVERAGE-2026-11-07.md.

ONE-ROUND REVIEW PROTOCOL (added 2026-11-08): before a language review, (1) reconcile coverage:
     every Japanese text block in the deliverable maps to exactly one checklist row (item or fixed
     text), and items in the source that are not printed are listed; (2) apply the same fixed checks
     to every row (reading, grammar, natural, one answer, key/gloss, level), decided in advance;
     (3) run one script check per issue type found so far over every row; (4) count only those
     checks as failures, style suggestions separately. A review that samples, or invents its
     criteria per round, finds new issues every round. Cross-ref: procedure-manual F.70.
